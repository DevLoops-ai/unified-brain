## Q1 — focused, security (SecureChannel tokens)

> After an OpenSecureChannel renew, which SecurityToken IDs does the server accept on incoming messages, how does it switch from the old token to the new one, and what happens when a token times out? Include what changed in commit 889e44517 and why TokenId zero matters.

Reference points (all in `src/ua_securechannel_crypto.c` unless noted):

- `checkSymHeader()` switches on `channel->renewState`:
  - `NORMAL` / `SENT` (default): `tokenId` must equal `securityToken.tokenId`, else `UA_STATUSCODE_BADSECURECHANNELTOKENUNKNOWN`.
  - `NEWTOKEN_SERVER`: the old token is still accepted **only if** `tokenId == securityToken.tokenId && tokenId != 0`; otherwise it must equal `altSecurityToken.tokenId`; on first use of the new token: `renewState = NORMAL`, `securityToken = altSecurityToken`, `altSecurityToken` re-initialised, then `UA_SecureChannel_generateLocalKeys()` **and** `generateRemoteKeys()`.
  - `NEWTOKEN_CLIENT`: the server may still use the old token (`altSecurityToken`, again `tokenId != 0`); when the new one is seen, `generateRemoteKeys()` only.
- Timeout: `token->createdAt + revisedLifetime * UA_DATETIME_MSEC`; if the channel is `OPEN` and past it → log "SecurityToken timed out", `UA_SecureChannel_shutdown(..., UA_SHUTDOWNREASON_TIMEOUT)`, return `UA_STATUSCODE_BADSECURECHANNELCLOSED`.
- `UA_SecureChannel_checkTimeout()`: if the **old** token expired while in `NEWTOKEN_SERVER`, it promotes `altSecurityToken` itself and regenerates both key sets before judging the timeout.
- Commit 889e44517 (`fix(core): don't accept TokenId zero as the old SecurityToken`): added the `&& tokenId != 0` conditions on both sides; in `src/server/ua_services_securechannel.c`, `lastTokenId` skips zero when it wraps ("TokenId zero is the placeholder"). Why: after the first OPN the placeholder token (id 0, no keys) was treated as "old token still in use", so a message with TokenId 0 was verified with never-derived keys — in Sign mode an HMAC with an empty key. Cites Part 4 §5.6.2 and Part 6 §6.7.2.3. Test added: `setupFirstToken()` in `tests/check_securechannel.c`.

Trap for grep: the renew logic is in `ua_securechannel_crypto.c`, not `ua_securechannel.c`.

## Q2 — broad, no single name (a Read request end to end)

> Trace a ReadRequest from bytes arriving on the TCP connection to the ReadResponse leaving, naming the functions at each stage: chunk and security processing, decoding and service lookup, session binding, the Read service's own checks, the per-node read, and how a read that cannot complete immediately is finished later.

Reference points:

- `src/server/ua_transport_tcp.c`: `serverNetworkCallback()` → `serverNetworkCallbackLocked()` → `processSecureChannelMessage()` (HEL/OPN/MSG dispatch; `processHEL`, `processOPN`, `processMSG`).
- Chunks: `UA_SecureChannel_processBuffer()` / chunk processing in `src/ua_securechannel.c`; symmetric header check `checkSymHeader()` and `decryptAndVerifyChunk()` in `src/ua_securechannel_crypto.c`; `unpackPayloadMSG()`.
- `processMSG()`: decodes the request, `getServiceDescription()` (`src/server/ua_services.c`, the `serviceDescriptions[]` table with `sessionRequired` and the counter offset), then `sendResponse()` (`ua_transport_tcp.c`).
- `processRequest()` (`ua_services.c`): `getBoundSession()` (defined in `ua_transport_tcp.c`) resolves the session from `requestHeader.authenticationToken`; if none and `sd->sessionRequired` → error (CloseSession special case); `notifyApplication(SERVICE_BEGIN)`, `beginModelChange()`, `processServiceInternal()`, `endModelChange()`, `SERVICE_END` or `SERVICE_ASYNC`; diagnostics counters.
- **`Service_Read()` lives in `src/server/ua_server_async.c`** (not in `ua_services_attribute.c`): checks `timestampsToReturn > NEITHER` → `BADTIMESTAMPSTORETURNINVALID`, `maxAge < 0` → `BADMAXAGEINVALID`, `maxNodesPerRead` → `BADTOOMANYOPERATIONS`, zero nodes → `BADNOTHINGTODO`; `allocateResultsArray()`; loop `Operation_Read()`; if an operation is not `done` → `persistAsyncResponseOperation(..., UA_ASYNCOPERATIONTYPE_READ_REQUEST, ...)`; session closed mid-loop → `BADSESSIONCLOSED`.
- `Operation_Read()` (`ua_services_attribute.c`): `UA_NODESTORE_GET_SELECTIVE` with the attribute mask; missing node → `BADNODEIDUNKNOWN`; `Operation_ReadWithNode()` → `readValueAttributeComplete()`; `UA_NODESTORE_RELEASE`.
- Async completion: the response is held in a `UA_AsyncResponse` and sent when the pending operations finish (ua_server_async.c).

Trap for grep: `Service_Read` is declared in `ua_services.h` and one would expect it in `ua_services_attribute.c`; it's in `ua_server_async.c`.

## Q3 — historical (a security fix and its reach)

> What did commit aa8ce3024 change, which functions were affected, what was the behaviour before and after for a client or server configured with an empty trust list, and where does the "accept-all" verifier it replaced come from?

Reference points:

- Commit `aa8ce3024`, 2026-09-15, "fix(config): apply certificate verification even for an empty trust list", one file: `plugins/ua_config_default.c` (+149/−167). Advisory `open62541-SA-2026-0057`.
- Three functions changed: `UA_ServerConfig_setDefaultWithSecurityPolicies()`, `UA_ServerConfig_setDefaultWithSecureSecurityPolicies()`, `UA_ClientConfig_setDefaultEncryption()`. The `if(trustListSize > 0) { … }` guard around building the `UA_TrustListDataType` and installing the trust-list verifier was removed; the copy now runs unconditionally (`UA_Array_copy()` handles a zero-length input).
- Before: with an empty list the step was skipped and the verifier already in the base config stayed — `UA_CertificateGroup_AcceptAll()` installed by the base default config (server: `secureChannelPKI` and `sessionPKI`; client: `certificateVerification`). After: an empty list yields a real verifier that trusts nothing.
- The trust-list verifier is `UA_CertificateGroup_Memorystore()` (`plugins/crypto/mbedtls/certificategroup.c` and `plugins/crypto/openssl/certificategroup.c`).
- Follow-up commit `031e62155` documents the behaviour change in the changelog.

## Q4 — PubSub (customer-shaped)

> How does a WriterGroup publish: how is the publishing interval scheduled, what does the publish callback do, how does a DataSetWriter decide between a key frame and a delta frame, and what happens to the WriterGroup and its connection when a network message cannot be sent?

Reference points (`src/pubsub/ua_pubsub_writergroup.c`, `src/pubsub/ua_pubsub_writer.c`):

- `UA_WriterGroup_addPublishCallback()`: registers `UA_WriterGroup_publishCallback` on the server's EventLoop with `el->addTimer(...)`, interval `wg->config.publishingInterval`, policy `UA_TIMERPOLICY_CURRENTTIME`, id stored in `wg->publishCallbackId` (no re-registration if already set); `UA_WriterGroup_removePublishCallback()` removes it.
- `UA_WriterGroup_publishCallback()`: `lockServer`; no `linkedConnection` → "Publish failed. PubSubConnection invalid", `UA_WriterGroup_setPubSubState(..., UA_PUBSUBSTATE_ERROR)`; reads `dataSetOrdering`, `includeClassId`, `singleJsonMessage` from the UADP/JSON message settings; builds and sends NetworkMessages (`generateNetworkMessage()`, `sendNetworkMessageBinary()` / `sendNetworkMessageJson()` → `sendNetworkMessageBuffer()`).
- Key vs delta: `UA_DataSetWriter_generateDataSetMessage()` uses `dsw->deltaFrameCounter` against `dsw->config.keyFrameCount`: a delta frame when `pds->fieldSize > 1 && deltaFrameCounter > 0 && deltaFrameCounter < keyFrameCount`, otherwise a key frame and the counter resets to 1; `keyFrameCount == 1` means always key frames (and a null PublishedDataSet requires `keyFrameCount == 1`).
- Send failure: `sendNetworkMessageBuffer()` sets **both** the WriterGroup and the PubSubConnection to `UA_PUBSUBSTATE_ERROR`; several other failure paths set the WriterGroup to ERROR; a failing writer sets `UA_DataSetWriter_setPubSubState(..., ERROR)`.

## Q5 — cross-cutting, no name in the question (session binding)

> How does the server decide whether a request needs a session, how does it find the session for a request, and what status does the client get when the token is unknown, when the session was closed or timed out, and when the session belongs to a different SecureChannel?

Reference points:

- `serviceDescriptions[]` in `src/server/ua_services.c`: per service, `sessionRequired` and the handler (e.g. `Service_Read` with `UA_SERVICECOUNTER_OFFSET(readCount, true)`); looked up by `getServiceDescription(requestTypeId)`.
- `getBoundSession()` (`src/server/ua_transport_tcp.c`): walks `channel->sessions` for a matching `authenticationToken`; `state == CLOSED` → `BADSESSIONCLOSED`; `validTill < now` → `BADSESSIONCLOSED`; not on this channel but found via `getSessionByToken()` → `BADSECURECHANNELIDINVALID` (and `unauthorizedRequestCount++` under diagnostics); not found at all → `BADSESSIONIDINVALID`.
- `processRequest()`: no session and `sd->sessionRequired` → return immediately; special case `CloseSessionRequest`: keeps `BADSESSIONCLOSED`, otherwise `BADSESSIONIDINVALID`.
- Also used from `ua_services_session.c` (ActivateSession path) via `rh->serviceResult = getBoundSession(...)`.
- Mid-service: `Service_Read` stops with `BADSESSIONCLOSED` if `session->state == UA_SESSIONSTATE_CLOSED` during the loop.

Trap for grep: "session" matches thousands of lines; `getBoundSession` is in the transport file, not the session file.
