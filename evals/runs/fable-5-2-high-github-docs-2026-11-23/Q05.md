# Answer

# Linear history plus required signed commits on `main`

## Short answer

- Linear history rules out the normal merge commit. Only **squash and merge** or **rebase and merge** remain.
- Required signed commits then makes **rebase and merge** on GitHub a problem, because GitHub cannot sign the rebased commits.
- In practice **squash and merge** is the method that works on GitHub (GitHub Free/Pro/Team and GitHub Enterprise Cloud). A rebase is still possible, but done locally with your own signature and then pushed.
- On GitHub Enterprise Server the documentation says you cannot merge pull requests into such a branch on GitHub at all; you merge locally, sign, and push.

## Which merge methods are left

**Effect of "Require linear history"**

- It prevents collaborators from pushing merge commits to the branch. Any pull request merged into the branch must use a squash merge or a rebase merge. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md; same text for rulesets in content/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets.md)
- The default **Merge pull request** option creates a merge commit, so it is no longer usable on `main`. (content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github.md)

**Effect of "Require signed commits" on each remaining method**

- The rule: contributors (and, on GitHub Free/Pro/Team and GitHub Enterprise Cloud, bots) can only push commits that are signed and verified to the branch. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md)
- Squash and merge (GitHub Free/Pro/Team, GitHub Enterprise Cloud): you can merge signed and verified commits into the branch using a pull request, and GitHub signs the final squash commit. (data/reusables/repositories/required-signed-commits.md)
- Rebase and merge: with this option the commits of the head branch are added to the base branch without commit signature verification. GitHub creates a modified commit from the original one, so GitHub did not truly create it and cannot sign it as a system user; GitHub also has no access to the committer's private signing key, so it cannot sign for the user. (data/reusables/pull_requests/rebase_and_merge_verification.md, included in content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github.md and content/authentication/managing-commit-signature-verification/about-commit-signature-verification.md)
  - The workaround given: rebase and merge locally, then push the changes to the pull request's base branch. (data/reusables/pull_requests/rebase_and_merge_verification_2.md)
  - Note: the documentation does not say in one sentence "the Rebase and merge button is blocked when signed commits are required". It says the two things above: the rebased commits carry no verified signature, and the branch accepts only signed and verified commits.
- GitHub Enterprise Server: with required signed commits "you cannot merge pull requests into the branch on GitHub". You can merge pull requests locally, but you must sign the resulting commit before pushing it to the branch. (data/reusables/repositories/required-signed-commits.md)

## How to enforce the linear history

1. Allow at least one linear merge method in the repository first. Before you can require a linear history, the repository must allow squash merging or rebase merging. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md; data/reusables/repositories/squash-and-rebase-linear-commit-history.md)
   - Repository **Settings** > General > "Pull Requests" > select **Allow squash merging** (and/or **Allow rebase merging**). (content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests.md; content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-rebasing-for-pull-requests.md)
2. Then turn the rule on, in one of two ways:
   - Branch protection rule for `main`: select **Require signed commits** and **Require linear history**. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule.md)
   - Ruleset: the rules "Require linear history" and "Require signed commits" exist there too. In a ruleset's "Require a pull request before merging" rule you can also require a merge type of merge, squash or rebase, so you can allow only squash. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets.md)

## Problems to expect

1. **Unsigned commits on the pull request branch can block a squash merge.** When GitHub checks whether a pull request can be merged, it creates a test merge commit and checks the commits this test merge introduces, including the commits from the head branch. So unsigned commits on the head branch can block a squash merge, even though GitHub would sign the final squash commit. This can also hit the author of the pull request. Fix: rewrite and sign the unsigned commits on the head branch, or ask someone with bypass permission to merge. (data/reusables/repositories/required-signed-commits.md, GitHub Free/Pro/Team and GitHub Enterprise Cloud)
2. **Fixing unsigned commits means rewriting history.** A collaborator who pushed an unsigned commit must rebase it to include a verified signature and then force push the rewritten commit. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md; content/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules.md)
3. **Rebase and merge on GitHub produces commits GitHub cannot sign** (see above). It also always changes the committer information and creates new commit SHAs, and it drops commits that were empty. (data/reusables/pull_requests/rebase_and_merge_summary.md)
4. **Local merges need a signature and maybe bypass rights.** You can squash and merge locally, but you must sign the resulting commit before pushing. If another protection requires changes to go through a pull request, you may also need bypass permissions to push the locally merged commit. (data/reusables/repositories/required-signed-commits.md)
5. **Rebase merging may need command-line work.** Contributors may have to rebase on the command line, resolve conflicts and force push to the pull request branch before "Rebase and merge" is available; force pushing must be done carefully. (content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github.md)
6. **Costs of squashing.** You lose the information about when specific changes were made and who authored the squashed commits; the original commit SHAs are lost; and if you keep working on the same head branch after a squash merge, later pull requests list the already squashed commits again and you may have to resolve the same conflicts repeatedly. (content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github.md; content/pull-requests/reference/pull-request-merges.md)
7. **Conflicting settings block merging.** If the repository disables a merge method and a ruleset requires that method, the merge is blocked. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets.md; content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github.md)
8. **Merge queue.** If you use a merge queue, you no longer choose the merge method on each pull request; the queue controls it. (content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github.md)
9. **Vigilant mode** (GitHub Free/Pro/Team, GitHub Enterprise Cloud): commits that GitHub marks "Partially verified" are permitted on branches that require signed commits. (content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md)
10. **GitHub Enterprise Server: web signing is optional.** GitHub signs commits made in the web interface only if a site administrator has enabled web commit signing. (content/authentication/managing-commit-signature-verification/about-commit-signature-verification.md)
