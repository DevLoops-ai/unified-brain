# Answer

xz deletes the original input in one place only: `io_unlink(pair->src_name, ...)`, called from `io_close_src()` in `src/xz/file_io.c`. For that to run, five things must all be true: the input is a real named file (not stdin), `--keep` is not in effect, the coding finished successfully, the output file closed without error, and the file at that name is still the one xz opened. Nothing else in `src/xz` deletes the input.

## 1. Where the deletion happens

`coder_run()` (`src/xz/coder.c`) always ends with `io_close(pair, success)`. `io_close()` (`file_io.c`) then:
1. Turns `success` false if writing the final sparse-file byte fails.
2. Blocks signals with `signals_block()`.
3. Copies file attributes with `io_copy_attrs()`, but only if `success` is true and the output is not stdout. Its result is not checked, so a failure here does not stop the deletion.
4. Calls `io_close_dest(pair, success)`. If that returns true, `success = false`. The comment there says: "If it fails, we must not remove the source file!"
5. Calls `io_close_src(pair, success)`.

`io_close_src()`:
```c
if (pair->src_fd != STDIN_FILENO && pair->src_fd != -1) {
    (void)close(pair->src_fd);
    if (success && !opt_keep_original)
        io_unlink(pair->src_name, &pair->src_st);
}
```
The input is closed before it is deleted. That order came in with commit e18adc56 ("Always close the file before trying to delete it"); the comment says older versions could fail with EBUSY on some CIFS shares.

## 2. All the conditions for deletion

**A. The input is a named file, not stdin.** The check is `src_fd != STDIN_FILENO` in `io_close_src()`. Input from stdin (`-`, or no file arguments; see the loop in `main()`, `main.c`) is never deleted. If `io_open_src()` failed, `coder_run()` returns before `io_close()` is ever called.

**B. `opt_keep_original` is false.** It becomes true in three ways:
- `-k` / `--keep` (`parse_real()`, `args.c`).
- `args_parse()` (`args.c`) forces it when `opt_stdout` is set or the mode is `MODE_TEST`: "Never remove the source file when the destination is not on disk." So `-c` / `--stdout`, `-t` / `--test`, and the `xzcat` / `lzcat` program names (which set `opt_stdout` in `args_parse()`) all keep the input.
- `--list` cannot delete either: `list_file()` calls `io_close(pair, false)` (`list.c`).

**C. Coding succeeded.** In `coder_run()`, `success` starts as false. It becomes true only if all of these hold:
- The first read (decompress/test mode) did not return `SIZE_MAX`.
- `coder_init()` did not return `CODER_INIT_ERROR`, and `user_abort` was not set.
- `io_open_dest()` succeeded. It fails, and nothing is deleted, if:
  - `suffix_get_dest_name()` returns NULL;
  - with `--force`, the old target file cannot be removed (an error other than ENOENT);
  - `open(O_CREAT|O_EXCL)` fails, so an existing target without `--force` blocks deletion;
  - on DJGPP, the target is a DOS special file or the same file as the input;
  - on Windows, the target is not a regular file.
- `coder_normal()` returns true. In its loop `while (!user_abort)`, success is set only when `lzma_code()` returns `LZMA_STREAM_END` and either:
  - trailing input is allowed (`--single-stream`, or `.lz` input; `allow_trailing_input` in `coder_init()`), or
  - the input is at EOF with nothing left over. Leftover bytes become `LZMA_DATA_ERROR`.

  Each of these breaks the loop with `success == false`:
  - any other non-OK return from liblzma (data, format, options or memory-limit errors);
  - `io_read()` returning `SIZE_MAX` (read error, EINTR during an abort, `IO_WAIT_ERROR`);
  - any `coder_write_output()` / `io_write_buf()` failure, including a write to a broken pipe (EPIPE).

  The remaining output is written before the end-of-stream check, so a failed final write also prevents deletion.
- Passthrough mode (`coder_passthru()`) is only used with `--decompress --stdout --force` (`coder_init()`). That implies `--keep`, so it can never delete the input.

**D. The output closed cleanly.** `io_close_dest()` returns true, which forces `success = false`, if:
- `close(dest_fd)` fails. In that case the output is also deleted.
- Restoring stdout's flags (`fcntl`) fails. This only happens when writing to stdout, where B or A already prevents deletion.

**E. The input file is still the same file** (`io_unlink()`). This check runs on non-DOS builds only:
- With `--force` it uses `stat()`, otherwise `lstat()`.
- If that call fails, or `st_dev` / `st_ino` differ from what `fstat()` recorded at open time (VMS compares only `st_ino`), xz prints "%s: File seems to have been moved, not removing" and does not delete.
- Otherwise it calls `unlink(name)`. If that fails, xz only prints "%s: Cannot remove: %s".
- The comments admit a small race between the stat and the unlink, and a known gap with `--force`: if foo is renamed to bar and a symlink foo -> bar is put in its place, `stat()` still matches, so the name foo is removed anyway.
- On DOS-like systems (`TUKLIB_DOSLIKE`) there is no identity check at all; xz just calls `unlink()`.

## 3. Checks at open time that stop deletion

These are in `io_open_src_real()`. Each one skips the file, so it never reaches the success path:
- Directories are always rejected.
- When output goes to disk (`!opt_stdout`), only regular files are accepted.
- Symlinks are rejected (`O_NOFOLLOW`, or `lstat()` where `O_NOFOLLOW` is missing) unless `--stdout`, `--force` or `--keep` is used.
- When output goes to disk and neither `--force` nor `--keep` is used (non-DOS only), these are rejected:
  - setuid or setgid bit set;
  - sticky bit set;
  - more than one hard link (`st_nlink > 1`).

  Commit 074259f4 ("Make --keep accept symlinks, hardlinks, and setuid/setgid/sticky") relaxed these checks for `--keep`, which is safe because nothing is deleted then.

So `--force` is the option that both allows deletion and removes these protections. With `-f`, xz can delete the name of a file that has other hard links, a setuid/setgid/sticky file, or a symlink. I read this from the checks above. That deleting a symlink's name removes only the link, not its target, is standard `unlink()` behaviour and is not written anywhere in this checkout. The code comment only says that with `--force`, "(de)compressing symlinks works correctly."

## 4. Things that do not stop deletion

- **Unsupported-check warning:** `LZMA_UNSUPPORTED_CHECK` is only a warning (`stop = false` in `coder_normal()`), and decoding goes on, so it can still end in success and delete the input. This warning is only requested when `--ignore-check` is not used (`coder_init()`).
- **Attribute copy errors:** failures in `io_copy_attrs()` are not looked at.
- **No fsync:** there is no `fsync` anywhere in `src/xz` at this commit. The input is deleted right after `close()` of the output, without forcing the output to disk first.
- **Late Ctrl-C:** signals are blocked only inside `io_close()`. If a signal arrives after `coder_normal()` has returned true but before `signals_block()`, `success` stays true and the input is still deleted. The coding had already finished at that point.
