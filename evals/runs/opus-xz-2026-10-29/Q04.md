# Answer

**Short answer:** nothing in this checkout checks that a test fixture's bytes are the expected bytes. There are no checksum manifests, no signatures and no git attributes for `tests/files/*`. The tests only check how the decoder behaves when it reads a fixture. For most `.xz` and `.lzma` files that means "decode succeeds" or "decode fails", and the decoded output is thrown away. Details below.

## 1. Behaviour checks (the main mechanism)

**`tests/test_files.sh`** (the whole script):
- `good-*.xz` must decode with `xz -dc` and with `xzdec`, and `unsupported-*.xz` must fail with `xz`. Output goes to `> /dev/null`, so only the exit status is checked, never the content.
- `bad-*.xz`, `bad-*.lzma` and `bad-*.lz` must fail. `xzdec` is skipped for bad `.xz` files when `NO_WARN` is set.
- One file is tested on its own: `bad-3-index-uncomp-overflow.xz` must fail `xz -l`.
- `unsupported-check.xz` must pass with `-qQ`.
- The script picks files by glob (`"$srcdir"/files/good-*.xz` and so on). Any new file matching a glob is picked up with no review step. Files can also be skipped when a feature is off (`have_feature`, exit 77).
- Stale entries: the `case` branches still name `good-1-sparc-lzma2.xz`, `good-1-x86-lzma2.xz` and `good-1-riscv-lzma2-*.xz`. Those files are gone (deleted in `e93e13c8` and `a5f2aa56`), so nothing flags missing fixtures.

**C unit tests, which check more than pass/fail:**
- `tests/test_lzip_decoder.c`, functions `basic_lzip_decode` and `trailing_helper`. These are the only tests that check the decoded content. They compute a CRC32 of the output and compare it to hard-coded values: `hello_world_crc = 0x15A2A343` and `trailing_garbage_crc = 0x87081A60`. `basic_lzip_decode` also checks `strm.total_in == file_size`.
- `tests/test_check.c`, functions `test_lzma_get_check_st` and `test_lzma_get_check_mt`. These check the return codes and the check type reported for `good-1-check-{none,crc32,crc64,sha256}.xz` and `unsupported-check.xz`. They do not check the output.
- `tests/test_bcj_exact_size.c`, function `test_empty_block`. For `good-1-empty-bcj-lzma2.xz` it checks `in_pos == in_size` and `out_pos == 0`, so every input byte must be consumed and no output produced.
- `tests/test_memlimit.c` checks memory-limit return codes on `good-unknown_size-with_eopm.lzma` and `good-1-check-crc32.xz`.

**`tests/test_scripts.sh`** checks the exit status of `xzdiff` on three fixtures. It also checks `xzgrep` output on `good-1-lzma2-1.xz` and `good-2-lzma2.xz`, comparing it byte for byte (`cmp -s`) with the committed `tests/xzgrep_expected_output`. This is an indirect content check of those two fixtures only.

## 2. Limits on how fixtures are loaded

`tests/tuktest.h`, function `tuktest_file_from_x` (used through the `tuktest_file_from_srcdir` macro):
- It rejects empty files.
- It rejects files over `TUKTEST_FILE_SIZE_MAX`, which is 64 MiB by default.
- It fails hard on open, seek, short-read and close errors.
- It is only a sanity check. It does not compare content.

- Bad files must be rejected the same way.
- Section 2 gives an expected description for each file.

No script checks that the README and the directory match, and I found no CPU or RAM limit applied when the fixtures run.

- It runs in the top-level `Makefile.am` `dist-hook` and `mydist` targets.

## Net assessment

Nothing in this checkout would detect extra data or a hidden payload inside a `good-*` or `bad-*` file, as long as the file still decodes (or fails) the way the test expects. The only content checks are:
- the CRC32 checks of `.lz` output in `test_lzip_decoder.c`,
- the `xzgrep` output comparison for two `.xz` files in `test_scripts.sh`,
- the "all input consumed" checks in `test_lzip_decoder.c` (`basic_lzip_decode`) and `test_bcj_exact_size.c`.
