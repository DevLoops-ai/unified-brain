# Answer

The `.note.GNU-stack` section comes from only two files in the tree: `src/liblzma/check/crc32_x86.S` and `src/liblzma/check/crc64_x86.S`. No C file, build script or linker setting adds it. Two things must both be true for it to appear in a built object.

## 1. The source check inside the assembly files

`crc32_x86.S` (end of file, after `LZMA_CRC32`, lines 301–308) and `crc64_x86.S` (lines 284–291) contain the same block:

```
#if defined(__ELF__) && (defined(__FreeBSD__) || defined(__linux__))
	.section	.note.GNU-stack,"",@progbits
#endif
```

The directive is emitted only when the target is ELF (`__ELF__`) and the OS is either Linux (`__linux__`) or FreeBSD (`__FreeBSD__`). The comment above it says it is "needed to support non-executable stack". The author also admits the OS test is a workaround: "It's ugly to use __FreeBSD__ and __linux__ here, but I don't know a way to detect when we are using GNU assembler."

On other ELF targets the build can still assemble these files, but the directive is left out. That covers NetBSD, OpenBSD, MirBSD and GNU/Hurd (CMake allows these), and `*bsd*` in configure. MinGW, Cygwin, MSYS and DJGPP are also allowed. I did not check here whether those targets define `__ELF__`. Either way, they define neither `__linux__` nor `__FreeBSD__`, so they never get the directive.

History (`git log` on `crc32_x86.S`):
- `e9f6e9c0` ("Added note.GNU-stack to x86 assembler files…") added the block with the check `defined(__ELF__) && defined(__linux__)`.
- `865e0a36` ("liblzma: Use non-executable stack on FreeBSD as on Linux", 2022-02-11) widened it to the current Linux-or-FreeBSD check in both files.

## 2. The build system must assemble these files

The `.S` files are compiled only when 32-bit x86 assembly is enabled and the build is not a "small" build:

**Autotools**
- `configure.ac` ("Assembler optimizations" section): `--enable-assembler` defaults to `yes`. That value becomes `x86` only when `host_os` matches `linux* | *bsd* | mingw* | cygwin | msys | *djgpp*` and `host_cpu` is `i?86`. Otherwise it becomes `no`. You can also pass `x86` or `no` directly. Choosing `x86` defines `HAVE_CRC_X86_ASM` and sets `AM_CONDITIONAL(COND_ASM_X86, …)`.
- `src/liblzma/check/Makefile.inc`:
  - `crc32_x86.S` is added under `if COND_ASM_X86`, inside the `else` branch of `if COND_SMALL`. So it is not built with `--enable-small` (`COND_SMALL` is set at `configure.ac:423`).
  - `crc64_x86.S` is added the same way, and additionally only inside `if COND_CHECK_CRC64`.

**CMake** (`CMakeLists.txt`)
- Lines 233–257: only when `NOT MSVC`. On MinGW, Cygwin, FreeBSD, GNU, Linux, MirBSD, NetBSD or OpenBSD, `ASM_I386_DEFAULT` comes from `check_symbol_exists("__i386__" …)`. On any other system it is `OFF`. The user can override it with `option(XZ_ASM_I386 …)`, and `enable_language(ASM)` runs only if that option is on.
- Lines ~711–739:
  - `crc32_x86.S` is added only when `NOT XZ_SMALL` and `XZ_ASM_I386`.
  - `crc64_x86.S` is added only when `"crc64" IN_LIST XZ_CHECKS`, `NOT XZ_SMALL` and `XZ_ASM_I386`.

**DOS** (`dos/Makefile`, `SRCS_ASM`): both `.S` files are always assembled. DJGPP does not define `__linux__` or `__FreeBSD__`, so the directive is never emitted there.

## Net result

The section is emitted only when building 32-bit x86 (i386/i?86) liblzma for an ELF target on Linux or FreeBSD, with assembly enabled (the autotools/CMake default on those hosts), and not as a small build (`--enable-small` / `XZ_SMALL`).
- The CRC32 object always gets it under those conditions.
- The CRC64 object gets it only if the CRC64 check is also enabled.

x86-64 and every other architecture build only C sources for these checks, so none of their objects contain the section. I found no build flag such as `-Wa,--noexecstack` or `-z noexecstack` anywhere in the checkout; my search pattern included `noexecstack` and nothing matched.
