# Answer

## Tracing the end-of-Stream path in the threaded xz decoder (checkout `45d08abc`)

All paths are relative to the checkout root. "MT" means `src/liblzma/common/stream_decoder_mt.c`, and "ST" means `src/liblzma/common/stream_decoder.c`.

**Short version.** Once Blocks are scheduled, the Stream parser only relies on the sizes declared in each Block Header. A worker later confirms each Block's real sizes and Check, and `SEQ_INDEX_WAIT_OUTPUT` makes sure every worker result has been delivered before any Index byte is read. After that, the Index, the Footer and the Padding are checked only against state the decoder computed itself. A recomputed CRC therefore does not help an attacker in any of the requested cases, with one exception: the next Stream Header's check-type field is protected only by its CRC, and that change is caught later by other checks.

---

### 0. How the CLI sets up the decoder

**Flags** (`src/xz/coder.c`, `coder_init`):
- `--ignore-check` sets `LZMA_IGNORE_CHECK`; otherwise `LZMA_TELL_UNSUPPORTED_CHECK` is set.
- `--single-stream` sets `allow_trailing_input = true`; otherwise `LZMA_CONCATENATED` is set.
- `LZMA_FAIL_FAST` is never set: grep for it in `src/xz/` finds nothing.

**Decoder choice and limits:**
- If `MYTHREAD_ENABLED` is defined, the CLI calls `lzma_stream_decoder_mt` with:
  - `memlimit_stop = hardware_memlimit_get(MODE_DECOMPRESS)` (`UINT64_MAX` if no limit is set);
  - `memlimit_threading = threads==1 ? 0 : hardware_memlimit_mtdec_get()`.
- Otherwise it calls `lzma_stream_decoder` (ST) with a single memory limit.
- `hardware_memlimit_mtdec_get` (`src/xz/hardware.c`) caps the threading limit at `memlimit_decompress`.
- `stream_decoder_mt_init` applies `my_max(1, …)` to both limits and clamps `memlimit_threading` to `memlimit_stop`.

**Main loop** (`coder_normal`):
- The action becomes `LZMA_FINISH` once `pair->src_eof` is true.
- Any return other than `LZMA_OK`, except `LZMA_UNSUPPORTED_CHECK`, sets `stop`. The CLI then writes out what it already has, prints `message_strm(ret)`, and breaks.
- On failure, `io_close(pair, false)` leads to `io_close_dest`, which unlinks the output file (`src/xz/file_io.c`). Output to stdout is not removed.
- Error texts (`src/xz/message.c`): `LZMA_DATA_ERROR` is "Compressed data is corrupt", `LZMA_BUF_ERROR` is "Unexpected end of input", `LZMA_MEMLIMIT_ERROR` is "Memory usage limit reached", `LZMA_OPTIONS_ERROR` is "Unsupported options".

**How `lzma_code` (`src/liblzma/common/common.c`) treats return values:**
- `LZMA_OK` with no input or output progress, twice in a row, becomes `LZMA_BUF_ERROR`.
- `LZMA_TIMED_OUT` becomes `LZMA_OK`.
- `LZMA_MEMLIMIT_ERROR`, `LZMA_*_CHECK` and `LZMA_STREAM_END` are non-fatal (`STREAM_END` moves to `ISEQ_END`).
- Every other error moves to `ISEQ_ERROR`, so later calls return `LZMA_PROG_ERROR`. More input cannot undo an error of this kind.

### 1. The success path in the MT decoder

#### A. The last Block finishes

**Main thread, `SEQ_BLOCK_THR_RUN`:**
- It copies input into `thr->in` until `in_filled == in_size`.
- `in_size` is `comp_blk_size()`, which is `vli_ceil4(compressed_size) + check_size`, taken from the Block Header.
- It then sets `coder->thr = NULL` and goes to `SEQ_BLOCK_HEADER`.
- The main thread never looks inside the Block. It jumps ahead by the size the header declared.

**Worker thread, `worker_decoder` calling `block_decode` (`src/liblzma/common/block_decoder.c`):**
- In `SEQ_CODE`, the input and output are limited to the header-declared sizes. It returns `LZMA_DATA_ERROR` if:
  - `comp_done && uncomp_done` but there is no end marker;
  - `comp_done` but the output is short;
  - `uncomp_done` but input is left over;
  - at `LZMA_STREAM_END`, `is_size_valid()` fails for either size.
- In `SEQ_PADDING`, any nonzero Block Padding byte is `LZMA_DATA_ERROR`.
- In `SEQ_CHECK`, a `memcmp` of `raw_check` against the computed check returns `LZMA_DATA_ERROR` on mismatch. This is skipped if `ignore_check` is set or the check type is not supported.

**When the worker ends** (`worker_decoder`, about lines 484–516), it does the following under `coder->mutex`:
- adds its progress to the main counters;
- sets `outbuf->finished = true` and `outbuf->finish_ret = ret`;
- if `ret` is an error and none is recorded yet, sets `thread_error`;
- calls `worker_stop()`, which subtracts `in_size` and `mem_filters` from `mem_in_use`, moves the filter memory to `mem_cached`, puts the thread back on `threads_free`, and signals `coder->cond`.

#### B. The Index is detected

- `decode_block_header` sees `in[*in_pos] == INDEX_INDICATOR` (0x00, defined in `index.h`) and returns `LZMA_INDEX_DETECTED`. The byte is not consumed.
- The sequence moves to `SEQ_INDEX_WAIT_OUTPUT`.

#### C. `SEQ_INDEX_WAIT_OUTPUT`: waiting for the workers

- It calls `read_output_and_wait(…, NULL, true, …)` and returns `LZMA_OK` until `lzma_outq_is_empty`.
- The source comment says the reason: "Flush the output from all worker threads so that we can decode the Index without thinking about threading."
- `lzma_outq_read` (`outqueue.c`) returns each buffer's `finish_ret` in Block order. A failed Block's error is therefore returned here, before any Index byte is read.

#### D. `SEQ_INDEX_DECODE`: checking the Index

`lzma_index_hash_decode` (`index_hash.c`) runs these steps:

| Step | What it checks | Result on failure |
|---|---|---|
| `SEQ_BLOCK` | the indicator byte | `DATA_ERROR` |
| `SEQ_COUNT` | the record count must equal `blocks.count` | `DATA_ERROR` |
| `SEQ_UNPADDED` | `UNPADDED_SIZE_MIN` (5) ≤ value ≤ `UNPADDED_SIZE_MAX` | `DATA_ERROR` |
| `SEQ_UNCOMPRESSED` | after `hash_append(&records, …)`, the running totals in `records` must not exceed those in `blocks` | `DATA_ERROR` |
| `SEQ_PADDING` | Index Padding bytes must be 0x00 | `DATA_ERROR` |
| `SEQ_PADDING` | `blocks_size`, `uncompressed_size` and `index_list_size` must be exactly equal between the two sides | `DATA_ERROR` |
| `SEQ_PADDING` | the `LZMA_CHECK_BEST` hashes of both sides must match | `DATA_ERROR` |
| `SEQ_CRC32` | the stored CRC32 must match the computed one | `DATA_ERROR` |

- When all steps pass, it returns `LZMA_STREAM_END`.
- VLIs (variable-length integers) must use the shortest encoding: `lzma_vli_decode` returns `DATA_ERROR` for a trailing 0x00 byte or more than 9 bytes (`vli_decoder.c`).

#### E. `SEQ_STREAM_FOOTER`

The decoder reads 12 bytes (returning `LZMA_OK` while it has fewer), then checks in this order:
1. `lzma_stream_footer_decode` (`stream_flags_decoder.c`):
   - Footer magic: a mismatch gives `FORMAT_ERROR`, which the caller turns into `DATA_ERROR`.
   - CRC32 mismatch: `DATA_ERROR`.
   - Reserved flag bits set: `OPTIONS_ERROR`.
   - `backward_size` is computed as `(stored + 1) * 4`.
2. `lzma_index_hash_size(index_hash) != footer_flags.backward_size` gives `DATA_ERROR`.
3. `lzma_stream_flags_compare(&coder->stream_flags, &footer_flags)` (`stream_flags_common.c`): different check types give `DATA_ERROR`. The Header's `backward_size` is `LZMA_VLI_UNKNOWN`, so only the check type is compared.

Then:
- If `concatenated` is false, it returns `LZMA_STREAM_END`.
- Otherwise it goes to `SEQ_STREAM_PADDING`.

#### F. `SEQ_STREAM_PADDING`

The decoder reuses `coder->pos` as a byte counter modulo 4.
- For each 0x00 byte: `pos = (pos + 1) & 3`.
- At the end of the input buffer:
  - without `LZMA_FINISH`: return `LZMA_OK`;
  - with `LZMA_FINISH`: return `pos==0 ? LZMA_STREAM_END : LZMA_DATA_ERROR`.
- At the first nonzero byte:
  - if `pos != 0`: consume that byte and return `LZMA_DATA_ERROR`;
  - otherwise call `stream_decoder_reset()`.

#### G. Starting the next Stream

- `stream_decoder_reset` re-initializes `index_hash` (both sides of the comparison and both hash states), and sets `sequence = SEQ_STREAM_HEADER` and `pos = 0`.
- It does **not** reset threads, the output-queue cache, `mem_cached`, `first_stream`, the memory limits or the progress counters.
- In `SEQ_STREAM_HEADER`, `lzma_stream_header_decode` checks the magic, then the CRC32, then the reserved bits.
  - Because `first_stream` is now false, `FORMAT_ERROR` becomes `DATA_ERROR`.
  - On success it copies `stream_flags.check` into `block_options.check`, and may return `LZMA_UNSUPPORTED_CHECK` (the CLI shows a warning and continues).
- Then `SEQ_BLOCK_HEADER` runs, then `SEQ_BLOCK_INIT`, which chooses threaded or direct mode (see section 5).

**The ST decoder** (`stream_decode`) has the same sequence: `SEQ_INDEX`, `SEQ_STREAM_FOOTER`, `SEQ_STREAM_PADDING` and `stream_decoder_reset`, with the same checks. It has no waiting step, because Blocks are decoded inline.

### 2. State that connects the stages

**`index_hash->blocks`** holds the totals (`blocks_size`, `uncompressed_size`, `count`, `index_list_size`) plus a running `LZMA_CHECK_BEST` hash of each `(unpadded, uncompressed)` pair. It is filled by `lzma_index_hash_append` at two different moments:
- **Threaded Block:** in `SEQ_BLOCK_INIT`, *before* decoding, using `lzma_block_unpadded_size(&block_options)` and the Block Header's `uncompressed_size`. The comment there says: "The Block decoder will verify the values while decoding." Those header-declared values are what the Index is later compared against. The worker's `is_size_valid` and padding checks are what make them true.
- **Direct-mode Block:** in `SEQ_BLOCK_DIRECT_RUN`, *after* `LZMA_STREAM_END`. Here `block_decode` has written the real sizes back into `coder->block_options` ("The caller may use this information to construct Index").

**`index_hash->records`** is built from the Index bytes and compared against `blocks`.

**`outbuf->finish_ret` and `thread_error`** carry each worker's result until the main thread reads it, in order, through `lzma_outq_read`.

**`coder->stream_flags`** comes from the Stream Header and is compared with the Footer flags.

**`lzma_index_hash_size()`** is calculated from `blocks.count` and `blocks.index_list_size`. After a successful Index decode these equal the `records` values, so the result is the exact size of the Index field that was read. That number is what gets compared with Backward Size.

**`first_stream`** decides whether a bad Header magic is reported as `FORMAT_ERROR` or `DATA_ERROR`.

**`coder->pos`** is reused: it holds the Footer byte count, then the Padding count modulo 4, then it is reset to 0.

### 3. Attacks, and what catches each one

**One rule about order:** inside the Index, all structural and cross-check comparisons happen *before* the CRC32 check (`SEQ_PADDING` then `SEQ_CRC32`). So a recomputed Index CRC never makes up for a wrong size.

#### (a) Index record with plausible but wrong Block sizes (CRC32 recomputed)

**Where it is caught:**
- Wrong count: `SEQ_COUNT`.
- Unpadded Size below 5: `SEQ_UNPADDED`.
- Running total exceeds the real total: `SEQ_UNCOMPRESSED`, checked per record.
- Totals or list size differ: `SEQ_PADDING`.
- Values swapped or shifted between records with the same totals and the same encoded lengths: only the `LZMA_CHECK_BEST` hash comparison catches this.

**Decoder state:**
- MT is in `SEQ_INDEX_DECODE`. The output queue is empty and all Stream output has already been delivered.
- The error is returned directly and never passes through `SEQ_ERROR`.

**Can more input change it?** No. The coder returns `LZMA_DATA_ERROR` (an `ISEQ_ERROR` error).

**What the CLI does:** prints "Compressed data is corrupt" and deletes the output file.

**What CRC alone would catch:** only the case where the CRC is *not* recomputed (`SEQ_CRC32`, test file `bad-2-index-4.xz`).

**My own inference, not stated in the source:** when `LZMA_CHECK_BEST` is SHA-256, the shortest-encoding rule plus all the checks above fix every byte of the Index before the CRC. So in streaming decode the Index CRC never catches anything the earlier checks would miss.

**Lying in both the Header and the Index:** if the attacker makes the Block Header and the Index agree on the same wrong sizes, the worker's block decoder catches the mismatch with the real data. The error arrives as a `finish_ret` in `SEQ_INDEX_WAIT_OUTPUT`, before the Index is read.

#### (b) Valid Index, but its size disagrees with the Footer's Backward Size (Footer CRC recomputed)

**Why only the Footer can be wrong:**
- The Index byte length is fixed by the Blocks: `count` and `index_list_size` must match, VLIs must be shortest-form, and the padding length is calculated from the records.
- So this case can only appear as a wrong Backward Size value in the Footer.

**Where it is caught:**
- In `SEQ_STREAM_FOOTER`, the `lzma_index_hash_size(...) != footer_flags.backward_size` check returns `LZMA_DATA_ERROR`.
- Backward Size is never used to locate anything in streaming decode. It is only compared.
- Without a recomputed CRC, `lzma_stream_footer_decode` returns `DATA_ERROR` from its CRC check.
- Wrong Footer magic gives `DATA_ERROR`. Reserved bits give `OPTIONS_ERROR`. A check type different from the Header gives `DATA_ERROR` from `lzma_stream_flags_compare`.

**Decoder state:** the output queue is empty, all output has been delivered, and the error is fatal.

**Truncated Footer:** while fewer than 12 bytes have arrived, the decoder returns `LZMA_OK`. More input can fix that. With `LZMA_FINISH`, `lzma_code` eventually returns `LZMA_BUF_ERROR`.

**Related limit:** `LZMA_BACKWARD_SIZE_MAX` is enforced earlier, inside `lzma_index_hash_append`.

#### (c) Stream Padding with a nonzero byte, or a length that is not a multiple of 4

No CRC is involved. Only the counter modulo 4 matters.

| Situation | Result | Can more input change it? |
|---|---|---|
| Nonzero byte while `pos != 0` | that byte is consumed and `DATA_ERROR` is returned | No |
| Nonzero byte while `pos == 0` | treated as the start of a new Stream, see (d); 0x00 is not 0xFD, so the magic fails and the result is `DATA_ERROR` | No |
| Input runs out with `pos != 0` and `LZMA_FINISH` | `DATA_ERROR` (test files `bad-0pad-empty.xz`, `bad-0catpad-empty.xz`) | No |
| Input runs out with `pos != 0`, no `LZMA_FINISH` | `LZMA_OK` | Yes, more zero bytes can fix it |

- Padding that is a multiple of 4, followed by EOF with `LZMA_FINISH`, returns `LZMA_STREAM_END`.
- The decoder does not check that the whole file length is a multiple of 4.

#### (d) Bytes after valid padding that look like a Stream Header but are partial or invalid

**Partial header (fewer than 12 bytes):**
- `SEQ_STREAM_HEADER` returns `LZMA_OK`. More input can complete it.
- At EOF the CLI keeps calling with `LZMA_FINISH`. `lzma_code` turns the second no-progress `LZMA_OK` into `LZMA_BUF_ERROR`, and the CLI prints "Unexpected end of input".
- A partial header cannot start with zero bytes, because those are counted as padding.

**Full 12 bytes, but invalid:**
- Wrong magic: `DATA_ERROR`, because this is not the first Stream (test file `bad-0cat-header_magic.xz`).
- Wrong CRC: `DATA_ERROR`.
- Reserved bits set with a valid CRC: `OPTIONS_ERROR`.

**Valid header that is truncated afterwards:** the decoder waits in `SEQ_BLOCK_HEADER`, which leads to `BUF_ERROR` in the same way.

**The one field only CRC protects:** if the attacker changes the check type and recomputes the CRC, the header decode cannot see it. It is caught later, either by Block decoding errors (the check size is now wrong) or at this Stream's Footer by `lzma_stream_flags_compare`.

**Decoder state:** in MT, the output queue is still empty here, because it was drained at the previous Index. The error is returned directly.

#### Concatenated mode vs single-Stream mode

**With `LZMA_CONCATENATED`:** everything above applies. `LZMA_STREAM_END` comes only at EOF with `LZMA_FINISH` (API documentation, `container.h`).

**Without it:**
- `SEQ_STREAM_FOOTER` returns `LZMA_STREAM_END` right after the flags compare. Padding and later bytes are never read.
- `xz --single-stream` sets `allow_trailing_input`, so `coder_normal` calls `io_fix_src_pos` and reports success. Bad padding, garbage, or an invalid second Stream are all **ignored**.
- Without `--single-stream`, the CLI always uses `LZMA_CONCATENATED` for .xz. The trailing-garbage check in `coder_normal` (which turns extra data into `DATA_ERROR`) only matters for .lzma and raw formats.

### 4. What has to wait for worker results

1. **The Block Check and the real sizes** are checked only in the worker. Their result reaches the main thread through `finish_ret`, in Block order (`lzma_outq_read`).
2. **The Index** must wait until the output queue is empty (`SEQ_INDEX_WAIT_OUTPUT`). Before that, `index_hash->blocks` holds header-declared sizes that have not yet been confirmed.
3. **Main-thread parsing runs ahead of the workers.** If a header lied, the main thread may already be reading bytes at the wrong position.
   - Without fail-fast, the first error in output order wins.
   - `read_output_and_wait` uses `pending_error = LZMA_PROG_ERROR` purely as a flag.
   - `SEQ_ERROR` drains output and returns the worker's `finish_ret` if an earlier Block failed; otherwise it returns `pending_error`.
4. **What must survive until the Index check:** each Block's `(unpadded, uncompressed)` pair, already added to the hash; and the per-Block `finish_ret` in its output buffer. A worker's input buffer is freed when it finishes.

---

### 5. Memory limits for the next Block

The decision is made in `SEQ_BLOCK_INIT` and `SEQ_BLOCK_THR_INIT`.

**Step 1: the hard limit.** If `mem_next_filters > memlimit_stop`:
- The decoder first flushes output with `read_output_and_wait(…, true, …)` and returns `LZMA_OK` while the output queue is not empty.
- Then it returns `LZMA_MEMLIMIT_ERROR`, and the sequence stays at `SEQ_BLOCK_INIT`.
- Only the filter memory is compared here (from `lzma_raw_decoder_memusage`), because direct mode does not need the input/output buffers.
- This check runs before `lzma_index_hash_append`, so a retry does not add the Block twice. The source says this check must come first so decoding can be restarted.
- **Through the API it is recoverable:** `lzma_memlimit_set`, then `stream_decoder_mt_memconfig`, then call again (test: `test_memlimit_stream_decoder_mt`, `tests/test_memlimit.c`).
- **The CLI treats it as fatal:** it prints "Memory usage limit reached" plus `message_mem_needed`, and deletes the output file.
- Only the first Block of the first Stream is pre-checked in `coder_init`. For Stream 2 the error comes in `coder_normal`, after Stream 1's output has already been written.

**Step 2: direct mode (single-threaded for this Block).** The decoder switches to `SEQ_BLOCK_DIRECT_INIT` if:
- either size is unknown or larger than `SIZE_MAX/3` (`is_direct_mode_needed`);
- the memory sum would overflow;
- or `mem_next_block` (filters + `comp_blk_size` + output-buffer memory) is larger than `memlimit_threading`.

In direct mode:
- It waits until the output queue is empty, then calls `threads_end`, which destroys all worker threads.
- It decodes inline and adds the real sizes to the Index hash after the Block.
- This is never an error. The API documentation says `memlimit_threading` "will never make lzma_code() return LZMA_MEMLIMIT_ERROR" (`container.h`).

**Step 3: a temporary shortage (this only delays scheduling).** The Block fits under `memlimit_threading`, but this condition fails: `memlimit_threading − mem_in_use − outq.mem_in_use ≥ mem_next_block`, plus a free output-queue slot and a free or creatable thread (`read_output_and_wait`).
- `SEQ_BLOCK_THR_INIT` drains output and waits on `coder->cond`, which `worker_stop` signals.
- It returns `LZMA_OK` if the output buffer is full. `LZMA_TIMED_OUT` is turned into `LZMA_OK` by `lzma_code`.
- Once the Block can start, it may free the output-queue cache (`lzma_outq_clear_cache2`) and cached Block decoders.
- No error results, and the Index is not affected.

**At a Stream boundary (my own inference from the code above):** when the first Block of the next Stream arrives, all of the previous Stream's workers have finished and the output queue is empty, so `mem_in_use` and `outq.mem_in_use` are both 0. So the temporary-shortage case cannot happen for that Block. It is either scheduled at once, sent to direct mode, or stopped with `LZMA_MEMLIMIT_ERROR`. That error is reported only after all earlier output has been delivered, and after the previous Stream's Index, Footer and Padding have already been fully checked.

**Observation (from reading the code, not tested):** after `LZMA_MEMLIMIT_ERROR`, `lzma_memusage` returns `stream_decoder_mt_memconfig`'s total. That is `mem_direct_mode + mem_in_use + mem_cached + outq.mem_allocated`, with a minimum of `LZMA_MEMUSAGE_BASE`. It does not include `mem_next_filters`. So the "X MiB required" message from the MT decoder may show less than the Block actually needs. The ST decoder sets `coder->memusage = memusage` before checking the limit, so it reports the real need.

### 7. Build and mode differences that change the path

- **No threading** (`MYTHREAD_ENABLED` not defined): the ST decoder runs with the same structural checks and one memory limit (`SEQ_BLOCK_INIT` returns `MEMLIMIT_ERROR` directly).
- **`-T1`**: `memlimit_threading` becomes 0, then 1, so every Block takes direct mode.
- **`LZMA_CHECK_BEST`** (`check/check.h`) is SHA-256, or CRC64, or CRC32, depending on what the build includes. With a CRC, the "swapped sizes" case in (a) is only protected by a non-cryptographic hash.
- **`FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION`** turns off the CRC32 checks in the Header, Footer and Index. The structural checks remain.
- **`--ignore-check`** turns off only the Block Check. The Index, Footer and Header checks still run.
- **Unsupported check type:** the Block Check is not verified, and the CLI shows a warning once per Stream.
- **`LZMA_FAIL_FAST`** (API only, not used by the CLI): worker errors are returned immediately, and truncation at a Block boundary returns `DATA_ERROR` instead of `BUF_ERROR`.
