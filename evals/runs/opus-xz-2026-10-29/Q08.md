# Answer

I traced two separate read paths. They check the Index very differently:

- **Path A, sequential decode.** Used by `lzma_stream_decoder` and `lzma_stream_decoder_mt`, which is what `xz -d` and `xz -t` run. It checks the Index against the Blocks it actually decoded.
- **Path B, reading backwards from the end of the file.** Used by `lzma_file_info_decoder`, which is what `xz --list` runs. It never decodes the Blocks, so it never compares the Index with them.

## Path A: sequential decode

While decoding, each finished Block adds its real Unpadded Size and real Uncompressed Size to the `blocks` side of an `lzma_index_hash` (`stream_decoder.c` `stream_decode`, SEQ_BLOCK_RUN, `lzma_index_hash_append`; the MT decoder does the same at `stream_decoder_mt.c:1295/1635`). The Index is then parsed by `lzma_index_hash_decode` (`index_hash.c`). The checks run in this order, and the first failure returns `LZMA_DATA_ERROR`:

| # | Check | Location |
|---|---|---|
| 0 | The decoder treats a byte as the start of the Index only if it is `0x00`. If the Index Indicator is changed to anything else, the byte is parsed as a Block Header. The Indicator check inside `index_hash` is then never reached from this decoder. | `stream_decode` SEQ_BLOCK_HEADER (`in[*in_pos] == INDEX_INDICATOR`) |
| 1 | Index Indicator byte. Only reachable when the API is called directly. | `lzma_index_hash_decode` SEQ_BLOCK |
| 2 | Number of Records must equal the number of Blocks decoded. | SEQ_COUNT |
| 3 | Each integer must be minimally encoded and at most 9 bytes. | `lzma_vli_decode` (`vli_decoder.c`) |
| 4 | Unpadded Size must be in `[UNPADDED_SIZE_MIN=5, UNPADDED_SIZE_MAX]`. | SEQ_UNPADDED |
| 5 | Running bound, checked after every Record: the Index totals so far must not exceed the Block totals (`blocks_size`, `uncompressed_size`, `index_list_size`). | SEQ_UNCOMPRESSED |
| 6 | Index Padding: the length comes from the Records, and every padding byte must be `0x00`. | SEQ_PADDING_INIT / SEQ_PADDING |
| 7 | Exact equality of the three totals. `blocks_size` sums `vli_ceil4(unpadded)`, not the raw Unpadded Size (`hash_append`). | SEQ_PADDING, "Compare the sizes" |
| 8 | Hash comparison. Each `(unpadded, uncompressed)` pair, stored as raw `lzma_vli` values in memory, is hashed on both sides with `LZMA_CHECK_BEST`, and the results must match. | `hash_append`, then the `memcmp` in SEQ_PADDING |
| 9 | CRC32 of the Index field. It is skipped when built with `FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION`. | SEQ_CRC32 |

After the Index, the Stream Footer is checked (`stream_decode` SEQ_STREAM_FOOTER, `lzma_stream_footer_decode` in `stream_flags_decoder.c`):

- Footer magic and Footer CRC32.
- Backward Size must equal `lzma_index_hash_size()`. That value is computed from the **blocks** side (`index_hash.c` `lzma_index_hash_size`), not from what was parsed.
- `lzma_stream_flags_compare` checks that the Header and the Footer carry the same Check ID.

Points that follow from this:
- **Changing the CRC32 alone does nothing for the attacker here.** The hash and the size checks (5–8) run *before* the CRC32 check (9). Recomputing the CRC32 after an edit still fails at 2–8.
- **Values equal means bytes equal.** Integers must be minimal (3), and the padding length is fixed by the values (6). So if the parsed values match the Blocks, every Index byte except the CRC32 is identical to the original. The only edit that reaches check 9 and fails only there is a change to the CRC32 field itself, or a hash collision at 8.
- **The Footer checks never catch an Index-only edit.** Once check 7 passes, the Index length is fully determined. So the Footer is always read at the right offset, and the Backward Size comparison is effectively against Block-derived data.
- **Hash strength depends on the build.** `LZMA_CHECK_BEST` is SHA-256 if it is built in, otherwise CRC64, otherwise CRC32 (`check/check.h`). `configure.ac --enable-checks=LIST` can leave SHA-256 out. With a CRC as the hash, an edit to several Records that keeps all three totals and collides the CRC is possible in principle, and the Index CRC32 can be recomputed. That is my reasoning; I did not build such a file. Even then, the decompressed output is unaffected, because Blocks are decoded from their own headers.

## Path B: reading backwards (`file_info.c` `file_info_decode`)

1. Footer magic and CRC32 (SEQ_FOOTER). The attacker did not touch the Footer, so this passes.
2. `file_target_pos >= backward_size + STREAM_HEADER_SIZE` (`file_info.c:390`).
3. Index decoder (`index_decoder.c` `index_decode`), in order:
   - Indicator byte.
   - Count against the memory limit. A huge count gives `LZMA_MEMLIMIT_ERROR`, not a data error.
   - Integer encoding (`lzma_vli_decode`).
   - Unpadded Size range.
   - `lzma_index_append` overflow and Backward Size maximum limits (`index.c:660–681`).
   - Zero padding.
   - CRC32.
4. The number of Index bytes consumed must equal Backward Size (`file_info.c:480`, `:495`).
5. `lzma_index_total_size + STREAM_HEADER_SIZE` must fit before the Index (`:519`). That total is Σ`vli_ceil4(unpadded)` (`index.c:1083`).
6. A Stream Header must be found at that computed offset, with valid magic and CRC32 (`lzma_stream_header_decode`, SEQ_HEADER_DECODE). If the offset is 0, the cached first header is used instead (`:525`).
7. Header and Footer flags must match (`lzma_stream_flags_compare`, SEQ_HEADER_COMPARE).
8. Size limits in `lzma_index_stream_padding` and `lzma_index_cat`.
9. The final `lzma_index_file_size == file_size` comparison (`:637`) is only an `assert`, not a runtime check.

**The gap:** individual Uncompressed Sizes, the order of Records, and individual Unpadded Sizes are not checked. Only their rounded total is checked, indirectly, by where the Stream Header is found. Any edit that keeps the Index the same length, keeps Σceil4(Unpadded Size), and recomputes the CRC32 passes `lzma_file_info_decoder` completely.

One possibility I did not test: if the total shrinks and the bytes at the new offset happen to form a valid Stream Header, check 6 passes. This could happen with raw bytes inside an LZMA2 uncompressed chunk of the original Blocks.

**Extra checks in `xz --list -vv` only.** These run at `V_DEBUG` (`list.c:887/941`), in `parse_block_header`, at the offset the Index gives:
- First byte must not be zero.
- `header_size` must not exceed what is available.
- Block Header CRC32 (`block_header_decoder.c:57`).
- `lzma_block_compressed_size` (`block_util.c`): Unpadded Size must exceed header + check size, and must match the header's Compressed Size field **if that field is present**.
- Uncompressed Size must match the header's Uncompressed Size field **if that field is present** (`list.c:516`).

**Applications that use the Index for random access.** If the Index sizes are fed into `lzma_block_decoder`, then `block_decode` rejects a mismatch: the `comp_done`/`uncomp_done` checks (`block_decoder.c:99–122`) and `is_size_valid` at the end of the Block (`:137`).

## Edits that pass one check but fail a later one

| Edit | Passes | Fails at |
|---|---|---|
| Overwrite only the CRC32 field | A 1–8 | A 9; B 3 (CRC32) |
| Any other edit with the CRC32 recomputed | B 3 (CRC32) | A 2–8, always before A 9 |
| Swap two Records | A 2–7 (all totals unchanged) | A 8. In B, passes all of 1–8. `--list -vv` fails at the Block Header read (CRC32) when the Unpadded Sizes differ, because the offsets move. |
| Unpadded Size 101→102 (same multiple of 4), CRC32 fixed | A 4, 5, 7 (ceil4 total unchanged); all of B; `-vv` if the header has no Compressed Size field | A 8; `-vv` `lzma_block_compressed_size` if the header has the field |
| Move bytes of Uncompressed Size between Records (+d / −d, same integer lengths), CRC32 fixed | A 2–7; all of B; `-vv` if the headers have no Uncompressed Size field | A 8; `-vv` `list.c:516` if they have the field; random-access `block_decoder.c:137` |
| Lower one Uncompressed Size | A 5 | A 7 |
| Raise one Uncompressed Size | — | A 5 (early exit) |
| Change one value so its integer length changes, CRC32 fixed | B 3 | A 5 or 7 (`index_list_size`); B 4 (Backward Size) |
| Change Σceil4 but keep the length, CRC32 fixed | B 3, 4 | A 7; B 5/6 (Stream Header at the wrong offset) |
| Non-minimal integer encoding | — | A 3 / B 3 |
| Non-zero padding byte | everything before the padding | A 6 / B 3, both before the CRC32 check |
| Change the Record count | — | A 2; B mostly 4, or a memory-limit error |
| Change the Index Indicator | — | A 0 (parsed as a Block Header, fails there); B 3 |

**Bottom line:** in Path A, the Blocks-vs-Index comparison (checks 2–8) is the real defence, and the CRC32 only adds coverage of its own 4 bytes. In Path B, the CRC32 plus the length and position checks are all there is, so an attacker who recomputes the CRC32 and keeps the length and the rounded block total gets past `--list`. The edit is only caught later, when the file is actually decoded with `xz -t` or `xz -d`.
