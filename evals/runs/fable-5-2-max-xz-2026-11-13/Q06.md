# Memory limit in the multithreaded .xz decoder (XZ Utils, commit 7baf6835)

Source: only files under `/tmp/xzmax/xz`. I read the code; nothing was compiled or run. The decoder is `/tmp/xzmax/xz/src/liblzma/common/stream_decoder_mt.c`; line numbers refer to it unless another file is named.

## Short answer

There are two limits, checked once per Block right after its Block Header is decoded. Both are compared against calculated sizes, not against real free memory.

- **`memlimit_threading` (soft)**: caps memory while Blocks are decoded in parallel. It never causes an error. A Block that does not fit either waits, or is decoded single-threaded ("direct mode").
- **`memlimit_stop` (hard)**: if the Block's filter chain alone needs more, `lzma_code()` returns `LZMA_MEMLIMIT_ERROR` after all earlier output is delivered. The error is resumable with `lzma_memlimit_set()`.

## 1. Limits and counters

`stream_decoder_mt_init()` (lines 1982-1985) takes both values from `lzma_mt` (`src/liblzma/api/lzma/container.h` lines 195-236):

```c
coder->memlimit_threading = my_max(1, options->memlimit_threading);
coder->memlimit_stop = my_max(1, options->memlimit_stop);
if (coder->memlimit_threading > coder->memlimit_stop)
	coder->memlimit_threading = coder->memlimit_stop;
```

Counters in `struct lzma_stream_coder` (lines 229-264) and in `lzma_outq` (`outqueue.h`):

| Field | Meaning |
|---|---|
| `mem_in_use` | filter chains + input buffers of running worker threads |
| `mem_cached` | filter chains kept by idle worker threads |
| `outq.mem_in_use` | output buffers currently in the output queue |
| `outq.mem_allocated` | all output buffers (in use + cached) |
| `mem_direct_mode` | filter chain of the single-threaded decoder (0 in threaded mode) |
| `mem_next_filters`, `mem_next_in`, `mem_next_block` | what the next Block needs |

## 2. What one Block costs

- `mem_next_filters = lzma_raw_decoder_memusage(coder->filters)` (state `SEQ_BLOCK_HEADER`, line 1206). It is the sum of each filter's `memusage()` plus `LZMA_MEMUSAGE_BASE` (`1 << 15`, `common.h` line 143); see `lzma_raw_coder_memusage()` in `filter_common.c`. A result of `UINT64_MAX` gives `pending_error = LZMA_OPTIONS_ERROR` and `SEQ_ERROR`.
- `mem_next_in = comp_blk_size(coder)`: the whole compressed Block, padded to 4 bytes, plus the check size.
- `mem_next_block = mem_next_filters + mem_next_in + lzma_outq_outbuf_memusage(uncompressed_size)` (line 1278). The last term is `sizeof(lzma_outbuf)` plus the whole uncompressed Block.

## 3. Checks in `SEQ_BLOCK_INIT` (lines 1221-1306), in this order

1. `mem_next_filters > memlimit_stop` → hard-limit path (case C below).
2. `is_direct_mode_needed()` is true for the compressed or uncompressed size (`LZMA_VLI_UNKNOWN` or `> SIZE_MAX / 3`) → `SEQ_BLOCK_DIRECT_INIT`.
3. `UINT64_MAX - mem_buffers < mem_next_filters` (the sum would overflow) → `SEQ_BLOCK_DIRECT_INIT`.
4. `mem_next_block > memlimit_threading` → `SEQ_BLOCK_DIRECT_INIT`.
5. Otherwise threaded mode: the direct-mode decoder is freed (`lzma_next_end(&coder->block_decoder, ...)`, `mem_direct_mode = 0`) and the state becomes `SEQ_BLOCK_THR_INIT`.

## 4. What happens when a Block does not fit

### Case A: fits alone, but not next to the Blocks running now → wait

`SEQ_BLOCK_THR_INIT` calls `read_output_and_wait()` with `&block_can_start`. The Block may start only when this holds (lines 751-763):

```c
coder->memlimit_threading - coder->mem_in_use - coder->outq.mem_in_use
		>= coder->mem_next_block
&& lzma_outq_has_buf(&coder->outq)
&& (coder->threads_initialized < coder->threads_max
		|| coder->threads_free != NULL)
```

- Until then the main thread copies finished output to the caller and sleeps on `coder->cond`. It consumes no new input.
- There is no explicit thread-count calculation. Fewer threads run simply because Blocks are not started; threads are created lazily in `initialize_new_thread()`.
- If the caller's output buffer fills first, `stream_decode_mt()` returns `LZMA_OK` and waits again on the next call. On timeout it returns `LZMA_TIMED_OUT`, which `lzma_code()` turns into `LZMA_OK`.

"In use" memory drops in two places:
- `worker_stop()` (lines 351-367), when a worker finishes: `mem_in_use -= in_size`, its filter memory moves from `mem_in_use` to `mem_cached`, and `coder->cond` is signalled.
- `move_head_to_cache()` in `outqueue.c`, when the main thread has copied a finished Block's whole output: `outq.mem_in_use` is reduced. So a caller that is slow to take output also delays new Blocks.

Cached memory is not in the start condition because it can be freed. Once the Block may start, with `mem_max = memlimit_threading - mem_next_block` (lines 1375-1424):
- If `mem_in_use + mem_cached + outq.mem_allocated > mem_max`, `lzma_outq_clear_cache2()` frees cached output buffers, keeping one if it has exactly the needed size.
- If a free thread exists and `mem_in_use + mem_cached + outq.mem_in_use > mem_max`, cached Block decoders of idle threads are freed with `lzma_next_end()`. The first one is kept when `thr->mem_filters <= mem_next_filters`.

Then the counters are updated (`mem_cached -= mem_freed; mem_in_use += mem_next_in + mem_next_filters;`) and the Block is set up: `lzma_outq_prealloc_buf()`, `get_thread()`, `lzma_block_decoder_init()`, input buffer `lzma_alloc()`, `lzma_outq_get_buf()`. The worker goes `THR_IDLE` → `THR_RUN` and the state becomes `SEQ_BLOCK_THR_RUN`.

### Case B: `mem_next_block > memlimit_threading` (or checks 2-3) → single-threaded direct mode, no error

`SEQ_BLOCK_DIRECT_INIT` (lines 1576-1616):
1. `read_output_and_wait()` until the output queue is empty (returns `LZMA_OK` to the caller while it is not).
2. `lzma_outq_clear_cache()` frees all cached output buffers.
3. `threads_end()` sets every worker to `THR_EXIT`, joins them, frees `coder->threads`, and zeroes `mem_in_use` and `mem_cached`.
4. `lzma_block_decoder_init(&coder->block_decoder, ...)` runs in the main thread, then `mem_direct_mode = mem_next_filters`.

`SEQ_BLOCK_DIRECT_RUN` decodes straight from the caller's input to the caller's output, with no per-Block buffers. Memory use can exceed `memlimit_threading`; the header says "even by a large amount". Afterwards the state returns to `SEQ_BLOCK_HEADER`, so the next Block is judged again and may go back to threads.

### Case C: `mem_next_filters > memlimit_stop` → `LZMA_MEMLIMIT_ERROR` (lines 1228-1241)

1. `read_output_and_wait(..., NULL, true, ...)` flushes pending output; while the queue is not empty the function returns `LZMA_OK`. `LZMA_FAIL_FAST` is not checked here.
2. When the queue is empty: `return LZMA_MEMLIMIT_ERROR`.

- The state stays `SEQ_BLOCK_INIT` and the decoded filter chain stays in `coder->filters`. The error does not go through `pending_error` / `SEQ_ERROR`.
- In `lzma_code()` (`src/liblzma/common/common.c` line 356) this code is in the non-fatal group, so the stream is not moved to `ISEQ_ERROR`.
- To resume, `lzma_memlimit_set()` calls `stream_decoder_mt_memconfig()`, and the next `lzma_code()` re-runs the check. A comment says the check is first in `SEQ_BLOCK_INIT` for exactly this reason.
- My inference: that Block is then decoded in direct mode, because the soft limit was capped to the old hard limit and cannot be raised later. This holds as long as the hard limit was never lowered below the soft one.

## 5. `stream_decoder_mt_memconfig()` (lines 1820-1864)

- Reports usage as `mem_direct_mode + mem_in_use + mem_cached + outq.mem_allocated`, with a minimum of `LZMA_MEMUSAGE_BASE`.
- Gets and sets only `memlimit_stop`. The comment says: "For now, memlimit_threading cannot be modified after initialization."
- A new limit below the reported usage returns `LZMA_MEMLIMIT_ERROR` and changes nothing. `lzma_memlimit_set()` turns 0 into 1.

## 6. How the `xz` tool uses it

In `/tmp/xzmax/xz/src/xz/coder.c` (lines 939-959), with limits from `/tmp/xzmax/xz/src/xz/hardware.c`:
- `memlimit_stop = hardware_memlimit_get(MODE_DECOMPRESS)`: the `--memlimit-decompress` value, or `UINT64_MAX` if not set (no hard limit by default).
- `memlimit_threading = threads == 1 ? 0 : hardware_memlimit_mtdec_get()`: the `--memlimit-mt-decompress` value, default `total_ram / 4` (capped at 1400 MiB on 32-bit builds), never above `--memlimit-decompress`. With one thread it is 0, so every Block goes to direct mode.
- On `LZMA_MEMLIMIT_ERROR` xz does not retry. It prints "Memory usage limit reached" plus `message_mem_needed(V_ERROR, lzma_memusage(&strm))` and fails the file (`coder_init()` lines 1021-1027, `coder_normal()` lines 1322-1342).

## 7. Not checked or not present in the code

- **Real memory**: nothing looks at free system memory. A failed allocation gives `LZMA_MEM_ERROR`, returned at once after `threads_stop()`, and it is fatal.
- **Direct mode vs. hard limit**: only the filter-chain estimate is compared with `memlimit_stop`.
- **No re-clamp**: `stream_decoder_mt_memconfig()` does not re-apply `memlimit_threading <= memlimit_stop` when the hard limit is lowered.
- **Reported usage after the error**: the sum in section 5 does not include `mem_next_filters`. So `lzma_memusage()`, and the "MiB of memory is required" line xz prints, show current allocations, not what the refused Block needs. The single-threaded decoder does store that number (`stream_decoder.c` line 229).
- **Init error**: `container.h` lists `LZMA_MEMLIMIT_ERROR` as a return value of `lzma_stream_decoder_mt()`, but I found no path in `stream_decoder_mt_init()` that returns it.
- **Tests**: `/tmp/xzmax/xz/tests/test_memlimit.c` (`test_memlimit_stream_decoder_mt()`) covers case C and resume. I found no test aimed at the soft limit's waiting or direct-mode switch.
