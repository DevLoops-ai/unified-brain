# How the .xz decoder separates Stream Padding, a new Stream, and trailing garbage

## Short answer

The decoder has no "garbage" detector. After a Stream Footer has passed all its checks, it enters state `SEQ_STREAM_PADDING` and asks two things about each next byte: is it `0x00`, and is the number of zero bytes so far a multiple of 4.

- Zero bytes are Stream Padding.
- The first non-zero byte on a 4-byte boundary is assumed to start a new Stream, which must then pass the normal Stream Header checks.
- Trailing garbage is simply input that fails one of those checks.

I read the source only; nothing was built or run.

## Where the logic lives

- **Single-threaded decoder:** `stream_decode()` in `src/liblzma/common/stream_decoder.c`. The states are `SEQ_STREAM_FOOTER` (l. 298-334), `SEQ_STREAM_PADDING` (l. 338-374) and `SEQ_STREAM_HEADER` (l. 113-157), plus `stream_decoder_reset()` (l. 85-98).
- **Threaded decoder:** `stream_decode_mt()` in `src/liblzma/common/stream_decoder_mt.c` has the same code (header l. 1034-1073, padding l. 1721-1759). The only addition is `++coder->progress_in`.
- **Header and footer parsing:** `lzma_stream_header_decode()` and `lzma_stream_footer_decode()` in `stream_flags_decoder.c`.
- **Constants:** `lzma_header_magic[6]` = `FD 37 7A 58 5A 00` and `lzma_footer_magic[2]` = `59 5A` in `stream_flags_common.c`; `LZMA_STREAM_HEADER_SIZE` = 12.

## What must be true before padding is looked at

1. **`LZMA_CONCATENATED` must be set** (`coder->concatenated`). Without it, `SEQ_STREAM_FOOTER` returns `LZMA_STREAM_END` right after the first footer (l. 330-331). Nothing after that is read; it stays in `next_in`.
2. **The footer must be valid.**
   - Wrong footer magic gives `LZMA_FORMAT_ERROR`, which is always converted to `LZMA_DATA_ERROR`.
   - A bad footer CRC32 gives `LZMA_DATA_ERROR`.
   - Reserved flag bits give `LZMA_OPTIONS_ERROR`.
   - Backward Size different from `lzma_index_hash_size()` gives `LZMA_DATA_ERROR`.
   - Header and footer flags that differ (`lzma_stream_flags_compare()`) give `LZMA_DATA_ERROR`.
3. **`coder->pos` is 0 on entry.** It is reused as the padding counter modulo 4: `coder->pos = (coder->pos + 1) & 3`. It survives across `lzma_code()` calls, so padding may be split over input chunks.

## The three cases (with `LZMA_CONCATENATED`)

| Input after a valid footer | Result |
|---|---|
| Input ends, `action == LZMA_FINISH`, `pos == 0` (no padding or a multiple of 4 zeros) | `LZMA_STREAM_END` |
| Input ends, `LZMA_FINISH`, `pos != 0` | `LZMA_DATA_ERROR` |
| Input ends, `action != LZMA_FINISH` | `LZMA_OK` (waits for more input) |
| Non-zero byte, `pos == 0` | New Stream: `stream_decoder_reset()` re-initialises `index_hash`, sets `SEQ_STREAM_HEADER` and `pos = 0`. The byte is not consumed; it becomes header byte 0. |
| Non-zero byte, `pos != 0` | The byte is consumed (`++*in_pos`) and `LZMA_DATA_ERROR` is returned, even if a fully valid Stream follows |
| New Stream, 12 bytes read, magic wrong | `LZMA_FORMAT_ERROR` converted to `LZMA_DATA_ERROR`, because `first_stream` is false (l. 127-129) |
| New Stream, magic right, CRC32 of Stream Flags wrong | `LZMA_DATA_ERROR` |
| New Stream, magic and CRC right, reserved bits set (`in[0] != 0x00 \|\| (in[1] & 0xF0)`) | `LZMA_OPTIONS_ERROR` |
| New Stream, fewer than 12 bytes before input ends | The decoder returns `LZMA_OK` whatever the action; `lzma_code()` turns this into `LZMA_BUF_ERROR` |

What this means for each case:

- **Valid padding** is only `0x00` bytes, with a count that is a multiple of 4, counted from the end of the footer. Empty padding is fine. Padding at the end of the file is fine, but only `LZMA_FINISH` confirms it.
- **A new Stream** is not recognised by peeking at the magic. Any non-zero byte on a 4-byte boundary ends the padding (code comment: "probably indicates beginning of a new Stream (or the file is corrupt)").
- **Trailing garbage** shows up in one of these ways:
  - Misaligned non-zero byte: `LZMA_DATA_ERROR`.
  - Aligned, 12 or more bytes, wrong magic: `LZMA_DATA_ERROR`.
  - Aligned, 1 to 11 bytes: `LZMA_BUF_ERROR`, so it looks like a truncated file.
  - Only zero bytes: accepted as padding if the count is a multiple of 4, otherwise `LZMA_DATA_ERROR`.
  - Garbage that starts with a valid Stream Header: decoded as a Stream, and the error comes later from normal Stream decoding.

The first Stream is special. `first_stream` is true until the first header decodes, so a wrong magic there stays `LZMA_FORMAT_ERROR`. The decoder starts in `SEQ_STREAM_HEADER`, so zero bytes before the first Stream are not accepted as padding.

## How the result reaches the caller

- **`lzma_code()`** (`src/liblzma/common/common.c`, l. 310-323): the first call with no progress returns `LZMA_OK`, the second in a row returns `LZMA_BUF_ERROR` (`allow_buf_error`). An application that sets `LZMA_CONCATENATED` but never sends `LZMA_FINISH` therefore gets `LZMA_BUF_ERROR` instead of `LZMA_STREAM_END`, even on a valid file.
- **`xz`** (`src/xz/coder.c`): sets `LZMA_CONCATENATED` unless `--single-stream` is given (l. 876-879). It switches to `LZMA_FINISH` at end of file (l. 1135, 1209). The messages come from `message_strm()`: "Compressed data is corrupt" for `LZMA_DATA_ERROR`, "Unexpected end of input" for `LZMA_BUF_ERROR`, "File format not recognized" for `LZMA_FORMAT_ERROR`.
- **`xz --single-stream`**: sets `allow_trailing_input = true` and omits the flag. At `LZMA_STREAM_END` it calls `io_fix_src_pos(pair, strm.avail_in)` and reports success (l. 1282-1287). Padding, further Streams and garbage are never examined.
- **xz's own "trailing garbage" check** (l. 1289-1315) is for .lzma and raw streams. For .xz, liblzma has already consumed all input when it returns `LZMA_STREAM_END`.
- **`xzdec`** (`src/xzdec/xzdec.c`): always uses `LZMA_CONCATENATED` (l. 182) and asserts `avail_in == 0` at the end (l. 258-262).

## Other decoders in the tree

- **`lzma_auto_decoder`** (`auto_decode()`): picks the format once from the first byte (`0xFD` means .xz) and passes the flags on. Its `SEQ_FINISH` check (`*in_pos < in_size` gives `LZMA_DATA_ERROR`) is commented as being for .lzma.
- **`lzma_stream_buffer_decode()`**: one call with `LZMA_FINISH`. A decoder `LZMA_OK` is mapped to `LZMA_DATA_ERROR` or `LZMA_BUF_ERROR`. As written, positions are restored (l. 54-55) before the `*in_pos == in_size` test (l. 68), so that test sees the start position.
- **`lzma_file_info_decoder`** (`file_info_decode()` in `file_info.c`, used by `xz --list` through `parse_indexes()` in `src/xz/list.c`) parses backward from the end of the file:
  - A file under 12 bytes gives `LZMA_FORMAT_ERROR`. After the first header, `file_size > LZMA_VLI_MAX || (file_size & 3)` gives `LZMA_DATA_ERROR` (l. 295-296).
  - `get_padding_size()` counts `0x00` bytes backward into `coder->stream_padding`. If `stream_padding & 3` is non-zero, the result is `LZMA_DATA_ERROR` (l. 337-338).
  - `reverse_seek()` gives `LZMA_DATA_ERROR` when fewer than `2 * LZMA_STREAM_HEADER_SIZE` bytes remain (l. 164-165).
  - The 12 bytes before the padding must decode as a footer. `hide_format_error()` turns a magic mismatch into `LZMA_DATA_ERROR` (l. 378-380), which is where trailing non-zero garbage fails.
  - The Stream start is found by arithmetic, not by scanning for magic: Backward Size, then `lzma_index_total_size() + LZMA_STREAM_HEADER_SIZE` (l. 509-523). The header is then decoded and compared (l. 594-606).
  - The padding size is stored with `lzma_index_stream_padding()`. The loop repeats until `file_target_pos == 0`.
- **.lz, for contrast**: `lzip_decode()` returns `LZMA_STREAM_END` at the first non-magic byte after one member, and xz sets `allow_trailing_input` for `FORMAT_LZIP` (l. 975). The .xz decoder has no such tolerance.

## Test files that show these cases

All are in `tests/files` and are run by `tests/test_files.sh` with `xz -dc` and `xzdec`.

- **Good:** `good-0pad-empty.xz` (Stream plus 4 zeros), `good-0cat-empty.xz`, `good-0catpad-empty.xz`.
- **Bad:**

  - `bad-0catpad-empty.xz`: 5 zeros between two Streams.
  - `bad-0cat-header_magic.xz`: second magic is `FD 37 7A 58 59 00`.
  - `bad-0cat-alone.xz`: a Stream followed by a .lzma file.

## Not checked or not present in the code

- There is no check of the absolute file offset; alignment is counted only from the end of the previous footer.
- There is no upper limit on padding length in the streaming decoders.
- There is no error code or message specific to "trailing garbage" for .xz.
- Streams are not required to share the same Check type. `LZMA_NO_CHECK`, `LZMA_UNSUPPORTED_CHECK` and `LZMA_GET_CHECK` can be returned again for each Stream.
- In `FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION` builds, header and footer CRC32 mismatches are not errors.
- No C unit test covers `SEQ_STREAM_PADDING`. `tests/test_index.c` has a TODO for `lzma_file_info_decoder` tests.
