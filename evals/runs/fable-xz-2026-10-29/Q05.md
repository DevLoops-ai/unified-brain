# Answer

All claims below come from the checkout at commit `45d08abc` (verified with `git log -1`), plus a build of that checkout that I used to confirm the edge cases empirically.

## Where the logic lives

The whole decision is made in one state, `SEQ_STREAM_PADDING`, of the single-threaded decoder `stream_decode()` in `src/liblzma/common/stream_decoder.c` (lines 338–374). The threaded decoder has a byte-for-byte equivalent in `stream_decode_mt()` in `src/liblzma/common/stream_decoder_mt.c` (lines 1721–1759); the only difference is that it also bumps `coder->progress_in`. Everything below applies to both.

This state is reached only when `LZMA_CONCATENATED` was given. Without the flag, `SEQ_STREAM_FOOTER` returns `LZMA_STREAM_END` right after a valid footer and the padding state is never entered (`stream_decoder.c:330-331`; `assert(coder->concatenated)` at line 339). `lzma_auto_decoder` just forwards the flag to `lzma_stream_decoder_init()` (`auto_decoder.c:57-60`), so it behaves the same for .xz input.

## The algorithm

After a Stream Footer validates, the decoder loops over input bytes (`stream_decoder.c:342-363`):

1. **Zero byte** → it is consumed as padding. `coder->pos = (coder->pos + 1) & 3` keeps a running count of padding bytes modulo 4 (line 362). There is no upper bound; the format spec (`doc/xz-file-format.txt` §2.2, lines 460-468) allows any multiple of four, including non-empty padding at end of file.

2. **Non-zero byte** → the loop breaks (lines 358-359). The comment says it "probably indicates beginning of a new Stream (or the file is corrupt)". The byte is *not* consumed here.
   - If `pos != 0` (padding length not a multiple of 4): consume that byte and return `LZMA_DATA_ERROR` (lines 367-370).
   - If `pos == 0`: `stream_decoder_reset()` is called, which resets the index hash and sets `sequence = SEQ_STREAM_HEADER` (lines 85-98, 373). The non-zero byte will be read as the first byte of a new Stream Header.

3. **Input exhausted** (`*in_pos >= in_size`, lines 343-354):
   - `action != LZMA_FINISH` → return `LZMA_OK`. The decoder cannot know whether more data follows; this is why the API doc says `LZMA_STREAM_END` is never returned under `LZMA_CONCATENATED` unless the caller uses `LZMA_FINISH` (`src/liblzma/api/lzma/container.h:681-684`).
   - `action == LZMA_FINISH` → `LZMA_STREAM_END` if `pos == 0`, else `LZMA_DATA_ERROR`.

So the decoder does **not** actually "recognize" a new stream in the padding state. It only distinguishes zero vs non-zero. The classification of a non-zero tail happens in `SEQ_STREAM_HEADER`.

## What happens to the non-zero tail (new stream vs garbage)

`SEQ_STREAM_HEADER` (`stream_decoder.c:113-157`) copies exactly `LZMA_STREAM_HEADER_SIZE` = 12 bytes (`api/lzma/stream_flags.h:25`) into `coder->buffer`, returning `LZMA_OK` until it has all 12 (line 119-120). Then `lzma_stream_header_decode()` in `src/liblzma/common/stream_flags_decoder.c:30-58` checks, in order:

- Magic `FD 37 7A 58 5A 00` (`stream_flags_common.c:15`) → mismatch gives `LZMA_FORMAT_ERROR`.
- CRC32 of the Stream Flags → mismatch gives `LZMA_DATA_ERROR`.
- Reserved bits (`in[0] != 0 || in[1] & 0xF0`, `stream_flags_decode()`) → `LZMA_OPTIONS_ERROR`.

The stream decoder then rewrites `LZMA_FORMAT_ERROR` to `LZMA_DATA_ERROR` when `!coder->first_stream` (`stream_decoder.c:128-129`); `first_stream` is set `true` in `lzma_stream_decoder_init()` (line 458) and cleared after the first header decodes (line 134). The comment at lines 70-74 explains the intent: "avoid misleading LZMA_FORMAT_ERROR in case the later Streams don't have valid magic bytes." `tests/files/README:152-159` documents this with `bad-0cat-header_magic.xz` (→ `LZMA_DATA_ERROR`) vs `bad-0-header_magic.xz` (→ `LZMA_FORMAT_ERROR`).

Therefore "trailing garbage" is never a distinct category inside liblzma. It is simply whatever fails Stream Header decoding, and the error code depends on how much of it there is:

- **≥ 12 bytes of non-magic garbage** → `LZMA_DATA_ERROR` (the rewritten `LZMA_FORMAT_ERROR`).
- **1–11 bytes of garbage, or a truncated real header** → the header state keeps returning `LZMA_OK` with no progress. The generic `lzma_code()` wrapper in `src/liblzma/common/common.c:311-323` turns the second consecutive no-progress `LZMA_OK` into `LZMA_BUF_ERROR`. So short garbage surfaces as `LZMA_BUF_ERROR`, not `LZMA_DATA_ERROR`. There is no test in `tests/*.c` for this .xz case (only the .lz decoder tests cover trailing bytes), so I verified it by building the checkout.
- **Exactly 12 bytes that happen to start with the magic** → `LZMA_DATA_ERROR` on the CRC check (or `LZMA_OPTIONS_ERROR` if the CRC happens to match and reserved bits are set).

## Empirical confirmation

I built liblzma and xz from this checkout with CMake (static, in a scratch directory), and ran a small harness (`/tmp/claude-0/-home-claude/ce40d89e-7892-5c0e-ade6-383cef3904e1/scratchpad/harness/pad_test.c`) that appends various tails to `tests/files/good-1-lzma2-1.xz`, feeds everything in one `lzma_code(LZMA_FINISH)` call and repeats until a non-OK result, for both `lzma_stream_decoder` and `lzma_stream_decoder_mt` with `LZMA_CONCATENATED`:

| Tail after valid stream | Result (ST and MT identical) |
|---|---|
| nothing / 4 zeros / 8 zeros | `LZMA_STREAM_END` |
| 5 zeros | `LZMA_DATA_ERROR` |
| 0 or 4 zeros + second stream | `LZMA_STREAM_END` |
| 5 zeros + second stream | `LZMA_DATA_ERROR` (second stream untouched: 423 bytes left) |
| 1, 3 or 11 garbage bytes | `LZMA_OK`, `LZMA_OK`, `LZMA_BUF_ERROR` |
| 12 garbage bytes (with or without 4-byte padding first) | `LZMA_DATA_ERROR` |
| magic + flags + wrong CRC | `LZMA_DATA_ERROR` |
| first 11 or 12 bytes of a real header, then EOF | `LZMA_OK`, `LZMA_OK`, `LZMA_BUF_ERROR` |

The `xz` binary from the same build maps these via `message_strm()` in `src/xz/message.c:806-816`: `LZMA_DATA_ERROR` → "Compressed data is corrupt", `LZMA_BUF_ERROR` → "Unexpected end of input", `LZMA_FORMAT_ERROR` → "File format not recognized". Confirmed: 5-byte padding and 12-byte garbage print "Compressed data is corrupt"; 3-byte garbage prints "Unexpected end of input"; `bad-0cat-header_magic.xz` prints "corrupt" while `bad-0-header_magic.xz` prints "not recognized".

## Two CLI-level details

- `xz --single-stream` does not pass `LZMA_CONCATENATED` and sets `allow_trailing_input = true` (`src/xz/coder.c:876-879`), so after the first `LZMA_STREAM_END` it stops reading and accepts anything that follows (`coder.c:1282-1287`). Confirmed: `xz -t --single-stream` on the 12-byte-garbage file succeeds.
- The "trailing garbage" check in `coder.c:1289-1316` (read one more byte after `LZMA_STREAM_END`, error with `LZMA_DATA_ERROR` if anything is there) exists for .lzma and raw streams, where liblzma itself does not consume trailing data; for .xz with `LZMA_CONCATENATED`, liblzma already consumed everything before returning `LZMA_STREAM_END`, so this check is a no-op. For LZMA_Alone decoded through `lzma_auto_decoder` with `LZMA_CONCATENATED`, `auto_decoder.c:98-105` (`SEQ_FINISH`) does the equivalent: any leftover input → `LZMA_DATA_ERROR`.

## Summary of the three cases

| Case | Recognized by | Becomes an error when |
|---|---|---|
| Stream padding | zero bytes after a valid footer, `SEQ_STREAM_PADDING` | count mod 4 ≠ 0 at a non-zero byte, or at `LZMA_FINISH` with input exhausted → `LZMA_DATA_ERROR` |
| Next stream | first non-zero byte after padding ends on a 4-byte boundary; decoded as a 12-byte Stream Header in `SEQ_STREAM_HEADER` | bad magic → `LZMA_DATA_ERROR` (would be `LZMA_FORMAT_ERROR` only for the first stream); bad CRC → `LZMA_DATA_ERROR`; reserved bits → `LZMA_OPTIONS_ERROR`; truncated → `LZMA_BUF_ERROR` via `lzma_code()` |
| Trailing garbage | not a separate concept; it is a failed Stream Header | ≥12 bytes → `LZMA_DATA_ERROR`; <12 bytes → `LZMA_BUF_ERROR` |
