## Summary

Short answer: this checkout has **no cryptographic or manifest-based integrity verification of test fixtures** (no checksum lists, signatures, size tables, or CI step that hashes `tests/files/*`). I searched for `sha256sum`, `SHA256SUMS`, `md5sum`, `checksum`, `.sig` across the tree and the only hits were unrelated (CRC check-type options in `build-aux/ci_build.bash`, and `test_lzip_decoder.c`, covered below). What exists instead is a set of **behavioral constraints**: the fixtures are validated indirectly by what the decoders do with them, plus a few content checks and reproducibility recipes. Details follow, grouped by mechanism.

### 1. Behavioral contract enforced at test time (`tests/test_files.sh`)

The fixture directory is split by filename prefix into three classes, and the test script enforces a pass/fail expectation per class (`tests/files/README`, section 1; `tests/test_files.sh`):

- `good-*.xz` must decode successfully with both `xz -dc` and `xzdec` (lines 61–108). A failure is "Good file failed" → exit 1.
- `bad-*.xz` must *fail* with `xz -dc` (and `xzdec` unless a check type was compiled out, line 119) (lines 110–124). A bad file that decodes is "Bad file succeeded" → exit 1.
- `unsupported-*.xz` must fail with `xz -dc` (lines 133–142), but `unsupported-check.xz` must pass with `-qQ` (lines 145–158).
- `bad-3-index-uncomp-overflow.xz` is additionally run through `xz -l`, which must fail (lines 126–131).
- Same good/bad pattern for `.lzma` (lines 165–181) and `.lz` (lines 188–206, gated on `HAVE_LZIP_DECODER`).

This is the strongest mechanism: any fixture whose bytes have been altered enough to flip its decode outcome breaks the test suite. Note what it does *not* catch: a change to a `bad-*` file that leaves it still-broken, or a change to a `good-*` file that leaves it still-valid (e.g. appended valid data). The README itself documents this as the fixture contract: "Good files must decode successfully without requiring a lot of CPU time or RAM … Bad files must cause the decoder to give an error" (`tests/files/README`, section 1).

The script also gates on build features via `have_feature()` (lines 39–46, 64–93) and skips with exit 77, so a missing decoder does not cause a false "fixture corrupt" failure. It still has `case` arms for `good-1-sparc-lzma2.xz`, `good-1-x86-lzma2.xz` and `good-1-riscv-lzma2-*.xz` (lines 74–93) although those files no longer exist in `tests/files/` (confirmed by `ls`); the glob simply never matches them.

### 2. Decoded-content checks in C tests (`tests/test_lzip_decoder.c`)

For the `.lz` fixtures, the tests go beyond pass/fail and assert the **decoded payload** against hard-coded CRC32 values:

- `hello_world_crc = 0x15A2A343` (CRC32 of `"Hello\nWorld\n"`) and `trailing_garbage_crc = 0x87081A60` (CRC32 of `"Trailing garbage\n"`), lines 27–31. The comment explains why CRCs instead of string literals: EBCDIC portability.
- `basic_lzip_decode()` (lines 35–75) decodes one byte at a time, accumulates `lzma_crc32()` over the output, asserts `strm.total_in == file_size` and `checksum == expected_crc`.
- `test_concatenated()` (lines 225–290) does the same for `good-2-v0-v1.lz`, `good-2-v1-v0.lz`, `good-2-v1-v1.lz`.
- `test_crc()` (lines 294–~340) asserts `bad-1-v1-crc32.lz` yields `LZMA_DATA_ERROR` and then decodes under `LZMA_IGNORE_CHECK`.
- `test_invalid_memlimit()` (lines 414–448) asserts the full-file consumption and `hello_world_crc` again for `good-1-v1.lz`.

So for the lzip fixtures specifically, the uncompressed content is pinned, not just the decode outcome. I found no equivalent payload CRC for any `.xz` or `.lzma` fixture: `tests/test_check.c` `main()` (lines 366–390) loads `good-1-check-{none,crc32,crc64,sha256}.xz` and `unsupported-check.xz` and `test_lzma_get_check_mt()`/`_st()` only assert the returned check type and `LZMA_STREAM_END`; `tests/test_memlimit.c` (lines 99–127, 164) and `tests/test_bcj_exact_size.c` `test_empty_block()` (lines 87–112) assert return codes and sizes consumed (`in_pos == in_size`, `out_pos == 0`), not content.

### 3. Loader-level sanity constraints (`tests/tuktest.h`, `tuktest_file_from_x()`)

Every C test reads fixtures through `tuktest_file_from_srcdir()` → `tuktest_file_from_x()` (lines 642–759). It is a hard error (test binary exits) if: filename NULL/empty, `fopen` fails, the file is empty (`end == 0`, line 728), the file exceeds `TUKTEST_FILE_SIZE_MAX` (default `64L << 20`, lines 620–623, 733), `fread` returns short (line 749), or `fclose` fails. The doc comment states the intent: "Empty files and files over TUKTEST_FILE_SIZE_MAX are rejected. The assumption is that something is wrong in these cases" (lines 636–637). This catches truncated-to-zero or wildly oversized fixtures, nothing finer.

### 4. Expected-output comparison for script tests (`tests/test_scripts.sh`, `tests/xzgrep_expected_output`)

- `xzdiff` is run on `good-1-check-crc32.xz` vs `good-1-check-crc64.xz` (must exit 0, i.e. identical payloads) and vs `good-1-lzma2-1.xz` (must exit 1) (lines 38–54). This implicitly pins that the first two fixtures decompress to the same bytes and the third to something different.
- `xzgrep` output over `good-1-lzma2-1.xz` and `good-2-lzma2.xz` is `cmp`'d byte-for-byte against the checked-in `tests/xzgrep_expected_output` (lines 65–81). That file contains the literal matched lines (`elit, sed do eiusmod tempor…`, `Hello`), so the decompressed text of those two `.xz` fixtures is effectively pinned, line by line, for the patterns `el`, `Hello`, `NOMATCH`.

### 5. Generated rather than stored fixtures (`tests/create_compress_files.c`, `tests/test_compress.sh`)

The round-trip inputs `compress_generated_{abc,random,text}` are not shipped; they are produced deterministically at test time by `create_compress_files` (`write_abc()`, `write_random()` with a fixed LCG seed `n = 5`, `write_text()` with seed `n = 29`; comment at line 93: "We always use the same random seed to generate identical files on all systems"). `test_compress.sh` `test_xz()` compresses, decompresses with `xz` and `xzdec`, and `cmp`'s against the original (lines 50–87). The file header states the motivation: "Using a test file generator program saves space in the source code package considerably." This design removes the fixture-integrity question for these inputs entirely, since there is no binary to tamper with. `tests/Makefile.am` `clean-local` deletes them; `tests.cmake` lines 157–172 build and run the same thing under CMake.
