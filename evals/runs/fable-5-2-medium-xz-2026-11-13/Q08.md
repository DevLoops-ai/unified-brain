# Q8: Attacker modifies the Index of a valid .xz file, Blocks untouched

There are two different code paths that read an Index, and they check very different things:

- **Path A - normal decompression** (`xz -d`, `xz -t`): `stream_decode()` in `src/liblzma/common/stream_decoder.c` and the threaded twin in `stream_decoder_mt.c`. The Index is never turned into an `lzma_index`; it is only *compared* against what the Blocks really were, via `lzma_index_hash` (`index_hash.c`).
- **Path B - Index-only reading** (`xz --list`): `file_info_decode()` in `file_info.c`, which uses the real Index decoder `index_decode()` (`index_decoder.c`) and reads the file backwards. Blocks are not decompressed, so the Index is mostly trusted.

## Path A: checks in the order they fire

While Blocks are decoded, `SEQ_BLOCK_RUN` calls `lzma_index_hash_append(index_hash, lzma_block_unpadded_size(&block_options), block_options.uncompressed_size)` after each Block. `hash_append()` updates, in `index_hash->blocks`: `blocks_size` (sum of `vli_ceil4(unpadded_size)`), `uncompressed_size`, `count`, `index_list_size` (sum of the VLI byte lengths of both fields) and a running `LZMA_CHECK_BEST` hash over the pair `{unpadded_size, uncompressed_size}`. `LZMA_CHECK_BEST` is SHA-256 if built in, else CRC64, else CRC32 (`check/check.h`). (In the threaded decoder the pair is appended from the Block Header values before the Block is decoded - `stream_decoder_mt.c` around line 1295 - and the Block decoder verifies those values; in direct mode it is appended after decoding, as in the single-threaded decoder.)

When the byte `INDEX_INDICATOR` (0x00) is seen where a Block Header would start, the state moves to `SEQ_INDEX` and `lzma_index_hash_decode()` runs. Its states and checks:

1. **`SEQ_BLOCK`** - first byte must be `INDEX_INDICATOR`, else `LZMA_DATA_ERROR`.
2. **`SEQ_COUNT`** - Number of Records must equal `blocks.count`, else `LZMA_DATA_ERROR`. Checked before any Record is read.
3. **VLI encoding** (`lzma_vli_decode()`, `vli_decoder.c`) - every VLI must be in its shortest form (a final `0x00` byte after the first byte is rejected) and at most `LZMA_VLI_BYTES_MAX` bytes.
4. **`SEQ_UNPADDED`** - each Unpadded Size must be within `UNPADDED_SIZE_MIN` (5) .. `UNPADDED_SIZE_MAX` (`LZMA_VLI_MAX & ~3`).
5. **`SEQ_UNCOMPRESSED`, running bound** - after each Record is added to `index_hash->records`, the running `records.blocks_size`, `records.uncompressed_size` and `records.index_list_size` must not *exceed* the Block totals. This is an early exit only, not an equality test.
6. **`SEQ_PADDING_INIT` / `SEQ_PADDING`** - Index Padding length is computed from the Records actually read (`(4 - index_size_unpadded(...)) & 3`) and every padding byte must be 0x00.
7. **Totals equal** - `blocks_size`, `uncompressed_size`, `index_list_size` must be exactly equal on both sides.
8. **Hash equal** - `lzma_check_finish()` on both, then `memcmp` of the two `LZMA_CHECK_BEST` digests. This is the only check that is sensitive to the *order* and the *exact per-Record values*.
9. **`SEQ_CRC32`** - CRC32 over the whole Index (Indicator through Padding) must match the stored 4 bytes. Disabled when `FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION` is defined.

Then back in `stream_decode()`, `SEQ_STREAM_FOOTER`:

10. `lzma_stream_footer_decode()` - footer magic `"YZ"` and the footer's own CRC32 (`stream_flags_decoder.c`).
11. **Backward Size** - `lzma_index_hash_size()` must equal `footer_flags.backward_size`. Note it is computed from `blocks.count` / `blocks.index_list_size` (the real Blocks), not from the Index bytes.
12. `lzma_stream_flags_compare()` - Check type in header and footer must match.
13. With `LZMA_CONCATENATED`: Stream Padding must be a multiple of 4 bytes (`SEQ_STREAM_PADDING`).

Independent of the Index but still relevant: the Block decoder (`block_decoder.c`) verifies each Block's real sizes against the Block Header fields (`is_size_valid`) and the Block Check. So the "truth" the Index is compared to is itself verified.

All of these return `LZMA_DATA_ERROR`. The Index error is reported only after all Blocks have been decoded and their output handed to the caller, since the Index is at the end. I did not check what the `xz` tool does with the already-written output file in that case.

## Path A: modifications that pass one check and fail a later one

| Modification | Passes | Caught by |
|---|---|---|
| Any edit, CRC32 left stale | possibly all of 1-8 | 9 (Index CRC32) - but see below, the earlier checks normally fire first |
| Any edit, CRC32 recomputed by attacker (CRC32 is not keyed) | 9 | 2, 5, 7 or 8 |
| Add or remove a Record | - | 2 (count) |
| Swap two Records whose fields have the same VLI lengths | 2, 4, 7 (all three sums unchanged), usually 5 | 8 (hash is order-sensitive) |
| Change an Unpadded Size without crossing a multiple of 4 (e.g. 5 -> 6), same VLI length | 2, 4, 5, 7 (`vli_ceil4` hides it) | 8 (hash) |
| Move N bytes of size from one Record to another (+N / -N), same VLI lengths | 2, 4, 7; 5 if the smaller one comes first | 8 (hash), or 5 mid-Index if a running sum overshoots |
| Raise a size so the total grows | 2, 4 | 5 as soon as the running sum exceeds the Block total |
| Lower a size so the total shrinks | 2, 4, 5 | 7 (totals not equal) |
| Change a value so its VLI is longer/shorter (sums otherwise kept) | 2, 4 | 5 or 7 via `index_list_size`; the shifted bytes also break 6, 9, 10, 11 |
| Re-encode a VLI in a non-minimal (padded) form | - | 3 |
| Non-zero Index Padding byte | 1-5 | 6 |
| Extra bytes appended to the Index | 1-9 (decoder stops after the CRC32) | 10 (footer magic/CRC read from the wrong place) |

Result for Path A: with SHA-256 built in, no Index change that alters any Record value or their order survives. The only "survivable" change is one that leaves every (Unpadded Size, Uncompressed Size) pair, their order, the encoding and the padding identical - i.e. no change at all. If liblzma is built without SHA-256/CRC64, check 8 is only a CRC64/CRC32 and could be collided on purpose.

## Path B: `xz --list` (`lzma_file_info_decoder`)

Checks in `file_info_decode()`:

- `SEQ_MAGIC_BYTES`: first Stream Header magic + CRC32; file size <= `LZMA_VLI_MAX` and a multiple of 4.
- `SEQ_PADDING_DECODE`: Stream Padding multiple of 4.
- `SEQ_FOOTER`: footer magic + CRC32; `backward_size + LZMA_STREAM_HEADER_SIZE` must fit before the footer.
- `SEQ_INDEX_DECODE` -> `index_decode()`: Index Indicator, minimal VLIs, Unpadded Size range, `lzma_index_append()` overflow limits (uncompressed sum, unpadded sum, file size <= `LZMA_VLI_MAX`, Index size <= `LZMA_BACKWARD_SIZE_MAX`), memory limit (`SEQ_MEMUSAGE`, `LZMA_MEMLIMIT_ERROR`), zero padding, Index CRC32.
- The Index decoder must consume exactly `backward_size` bytes (`index_remaining` must be 0 at `LZMA_STREAM_END`, and it must not ask for more).
- `seek_amount = lzma_index_total_size() + LZMA_STREAM_HEADER_SIZE` must not go before the start of the file, and the place it lands on must decode as a valid Stream Header (`SEQ_HEADER_DECODE`: magic + CRC32), or be offset 0.
- `SEQ_HEADER_COMPARE`: `lzma_stream_flags_compare()` header vs footer.

What is **not** checked here: there is no `lzma_index_hash`, the Blocks are not read, and nothing compares the Records to the real Blocks. The Uncompressed Size fields are not validated against anything. The Record count is not validated against anything. The individual Unpadded Sizes are only constrained through their total (the sum of `vli_ceil4(unpadded)` must make the backward seek land on the Stream Header).

So an attacker who recomputes the Index CRC32 and keeps the Index byte length and the total padded Block size can:
- claim any Uncompressed Sizes (same VLI lengths, or lengths compensated elsewhere),
- move Block boundaries around, or change the number of Records, as long as the totals still add up.

Plain `xz -l` will then print wrong numbers with no error.

Extra checks in the `xz` tool (`src/xz/list.c`), only in the verbose/robot modes that call `parse_details()` -> `parse_block_header()`:
- the byte at each claimed Block offset must not be 0x00 (that would be an Index Indicator),
- `lzma_block_header_decode()` must succeed at that offset (Block Header has its own CRC32), and the header size must fit,
- `lzma_block_compressed_size(&block, iter->block.unpadded_size)`: Unpadded Size must be larger than header + Check, and must agree with the Compressed Size field **if the Block Header has one**,
- Uncompressed Size from the Index must equal the Block Header field **if present**.

So a moved Block boundary that survives `xz -l` fails `xz -lvv` (the fake offset does not hold a valid Block Header). A wrong Uncompressed Size survives `xz -lvv` too when the Block Header has no Uncompressed Size field, and is only caught by a real decode (`xz -t`, Path A, check 7/8). `parse_check_value()` just prints the bytes at the claimed Check position; it verifies nothing.

## Summary

- Integrity of the Index bytes themselves: Index CRC32 (weak, attacker can recompute), VLI minimal form, zero padding, Unpadded Size range.
- Consistency with the Stream: Backward Size in the footer, footer magic/CRC, header/footer flags, backward seek landing on a Stream Header (Path B).
- Consistency with the Blocks: count, three running/total sums, and the `LZMA_CHECK_BEST` hash - only in Path A (full decode). This is the check that cannot be worked around.
- Gap: the Index-only path (`lzma_file_info_decoder`, `xz --list`) does not bind the Index to the Blocks; a self-consistent forged Index passes there and only fails later, partly in `xz -lvv`, fully in a real decompression.
