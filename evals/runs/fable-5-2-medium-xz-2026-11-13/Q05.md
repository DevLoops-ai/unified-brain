# Answer

# How the .xz decoder tells stream padding, a new stream, and trailing garbage apart

## Short answer

The decoder has no "trailing garbage" category. After a Stream Footer, with `LZMA_CONCATENATED` set, it knows only two things: a `0x00` byte is Stream Padding, and any non-zero byte must be the first byte of a new Stream Header. Anything that is neither valid padding nor a valid new stream is an error, normally `LZMA_DATA_ERROR`.

The logic is in `stream_decode()` in `src/liblzma/common/stream_decoder.c`, state `SEQ_STREAM_PADDING` (lines 338-374). The threaded decoder has the same logic in `src/liblzma/common/stream_decoder_mt.c` (lines 1721-1759).

## When the padding state is reached

- `SEQ_STREAM_FOOTER` first validates the footer: `lzma_stream_footer_decode()`, then Backward Size against `lzma_index_hash_size()`, then `lzma_stream_flags_compare()` against the header.
- A bad footer magic (`LZMA_FORMAT_ERROR`) is converted to `LZMA_DATA_ERROR`.
- If `coder->concatenated` is false, the decoder returns `LZMA_STREAM_END` right after the footer and never looks at later bytes.
- If it is true (flag `LZMA_CONCATENATED`, value 0x08, set in `lzma_stream_decoder_init()`), it moves to `SEQ_STREAM_PADDING`.

## Case 1: stream padding

- The loop consumes each `0x00` byte and counts it modulo 4: `coder->pos = (coder->pos + 1) & 3`.
- When input runs out:
  - action is not `LZMA_FINISH`: returns `LZMA_OK` and waits, because more input may come.
  - action is `LZMA_FINISH` and `coder->pos == 0`: returns `LZMA_STREAM_END`. This is the only successful end in concatenated mode.
  - action is `LZMA_FINISH` and `coder->pos != 0`: returns `LZMA_DATA_ERROR`, because padding must be a multiple of 4 bytes.
- Empty padding (0 bytes) is valid.
- No upper limit on padding length is checked in this state.

## Case 2: start of another stream

- The first non-zero byte ends the loop. The byte is not consumed.
- If `coder->pos != 0` (padding so far is not a multiple of 4): the decoder consumes that one byte (`++*in_pos`) and returns `LZMA_DATA_ERROR`.
- Otherwise it calls `stream_decoder_reset()`, which re-initialises the index hash (`lzma_index_hash_init()`, `LZMA_MEM_ERROR` on failure), sets `sequence = SEQ_STREAM_HEADER` and `pos = 0`.
- `SEQ_STREAM_HEADER` then collects `LZMA_STREAM_HEADER_SIZE` (12) bytes and calls `lzma_stream_header_decode()` (`stream_flags_decoder.c`):
  - magic is not `FD 37 7A 58 5A 00` (`lzma_header_magic`): `LZMA_FORMAT_ERROR`
  - CRC32 of the Stream Flags is wrong: `LZMA_DATA_ERROR`
  - reserved flag bits set (`in[0] != 0` or `in[1] & 0xF0`): `LZMA_OPTIONS_ERROR`
- From there the new stream is decoded like the first one, with all the usual block, index and footer checks.

## Case 3: trailing garbage

- Garbage is simply a non-zero byte that fails the Case 2 header check.
- The key detail is `coder->first_stream`. It starts as `true` in `lzma_stream_decoder_init()` and is set to `false` after the first header decodes successfully. `stream_decoder_reset()` does not set it back.
- The header state returns `ret == LZMA_FORMAT_ERROR && !coder->first_stream ? LZMA_DATA_ERROR : ret`.
  - Bad magic on the first stream: `LZMA_FORMAT_ERROR` (file format not recognised).
  - Bad magic on any later stream: `LZMA_DATA_ERROR` (corrupt data). The comment on the struct field says this avoids a misleading format error.
- Garbage made only of zero bytes is treated as padding, so it fails only if its length is not a multiple of 4.
- Garbage shorter than 12 bytes (or a truncated next header) at `LZMA_FINISH`: `SEQ_STREAM_HEADER` returns `LZMA_OK` because `pos < 12`, and never `LZMA_STREAM_END`. I did not read the full no-progress branch of `lzma_code()` in `common.c`; from the `allow_buf_error` lines I did read, a repeated no-progress call is turned into `LZMA_BUF_ERROR`. The one-shot `lzma_stream_buffer_decode()` (`stream_buffer_decoder.c`, which always passes `LZMA_FINISH`) turns `LZMA_OK` with all input used into `LZMA_DATA_ERROR`.

## Summary table

| Bytes after the Stream Footer | Result |
|---|---|
| End of input, `LZMA_FINISH`, zero count is a multiple of 4 | `LZMA_STREAM_END` |
| End of input, `LZMA_FINISH`, zero count is not a multiple of 4 | `LZMA_DATA_ERROR` |
| End of input, no `LZMA_FINISH` | `LZMA_OK` (waits) |
| Non-zero byte after a zero count that is not a multiple of 4 | `LZMA_DATA_ERROR` (one byte consumed) |
| Non-zero byte, aligned, valid 12-byte header | next stream is decoded |
| Non-zero byte, aligned, wrong magic | `LZMA_DATA_ERROR` (would be `LZMA_FORMAT_ERROR` only on the first stream) |
| Header magic fine, CRC32 wrong | `LZMA_DATA_ERROR` |
| Header magic and CRC fine, reserved bits set | `LZMA_OPTIONS_ERROR` |
| Fewer than 12 bytes left at `LZMA_FINISH` | no `LZMA_STREAM_END`; `LZMA_BUF_ERROR` via `lzma_code()`, `LZMA_DATA_ERROR` in the buffer API |

## Related code paths

- **`xz` tool** (`src/xz/coder.c`): sets `LZMA_CONCATENATED` unless `--single-stream` is given. `coder_normal()` switches to `LZMA_FINISH` when `pair->src_eof` is true. With `--single-stream`, `allow_trailing_input = true`: on `LZMA_STREAM_END` it calls `io_fix_src_pos()` and reports success, so trailing data is ignored without an error. Without `allow_trailing_input`, `xz` itself tries to read one more byte after `LZMA_STREAM_END` and sets `LZMA_DATA_ERROR` if input remains; the comment says this is for `.lzma` and raw streams, and not for `.lz`.
- **`auto_decoder.c`**: picks the format from the first byte (`0xFD` = .xz). Its `SEQ_FINISH` state returns `LZMA_DATA_ERROR` if input remains after `LZMA_STREAM_END` in concatenated mode. The comment says this is for `.lzma` files; for .xz the stream decoder has already consumed everything by then.
- **`file_info.c`** (reads the file backwards, used for listing): `SEQ_PADDING_DECODE` counts the zero bytes at the end with `get_padding_size()` and returns `LZMA_DATA_ERROR` if `coder->stream_padding & 3`. `lzma_index_stream_padding()` in `index.c` rejects a padding value that is not a multiple of 4 or is above `LZMA_VLI_MAX`. I did not trace the rest of `file_info.c`.

## Not checked in the code

- Stream Padding has no maximum size in `SEQ_STREAM_PADDING`.
- Nothing verifies that non-zero trailing bytes are "garbage" as such; they are always tried as a Stream Header.
- Without `LZMA_CONCATENATED`, liblzma does not check bytes after the first stream at all; that is left to the caller.
