# Answer

# Q7: When can xz delete the original input file, and what can prevent it?

## Short answer

There is exactly one place where the source file is removed: `io_close_src()` in `src/xz/file_io.c`, which calls the static helper `io_unlink(pair->src_name, &pair->src_st)`. It runs only when all of these are true:

1. The source is a real opened file: `pair->src_fd != STDIN_FILENO && pair->src_fd != -1`.
2. `success` is true (coding finished without error and the destination file was closed without error).
3. `opt_keep_original` is false.
4. Inside `io_unlink()`: the path still exists and still has the same device and inode numbers as the file xz opened; then `unlink()` itself must succeed.

The source is always `close()`d first, then unlinked.

## The call chain

- `main()` (`src/xz/main.c`) calls `coder_run(filename)` for each name (or `list_file()` in `--list` mode).
- `coder_run()` (`src/xz/coder.c`): `io_open_src()` -> `coder_init()` -> `io_open_dest()` -> `coder_normal()` or `coder_passthru()` -> `io_close(pair, success)`.
- `io_close()` (`file_io.c`): writes the final sparse byte if needed, `io_copy_attrs()`, then `io_close_dest(pair, success)`, then `io_close_src(pair, success)`.
- `io_close_src()`: `close(src_fd)`, then `if (success && !opt_keep_original) io_unlink(...)`.

## Condition 1: `opt_keep_original` must be false

`opt_keep_original` (`src/xz/args.c`, default `false`) becomes true when:

- `-k` / `--keep` is given.
- `opt_stdout` is set or the mode is `MODE_TEST`. In `args_parse()`:
  `if (opt_stdout || opt_mode == MODE_TEST) { opt_keep_original = true; opt_stdout = true; }`
  (comment: "Never remove the source file when the destination is not on disk").
  `opt_stdout` is set by `-c`/`--stdout`, and also by the program name handling in `args.c` (lines 774-781, the `opt_mode = MODE_DECOMPRESS; opt_stdout = true;` cases for the "cat"-style names).

So deletion is only possible in `MODE_COMPRESS` or `MODE_DECOMPRESS` with a file on disk as output.

`--list` mode: `list_file()` (`src/xz/list.c`) always calls `io_close(pair, false)`, so the file is never removed there.

## Condition 2: the source must be a real file, not stdin

`io_close_src()` skips everything when `src_fd` is `STDIN_FILENO` or `-1`. Stdin is used when the name is `-` (or no names were given); `main()` replaces it with the `stdin_filename` pointer and `io_open_src_real()` sets `src_fd = STDIN_FILENO`.

## Condition 3: `success` must be true

`coder_run()` starts with `bool success = false` ("Assume that something goes wrong"). It only becomes true from the return value of `coder_normal()` / `coder_passthru()`. It stays false, so no deletion, when:

- The first read fails in decompress mode (`io_read()` returns `SIZE_MAX`).
- `coder_init()` returns `CODER_INIT_ERROR`, or `user_abort` is already set.
- `io_open_dest()` fails. Reasons in `io_open_dest_real()` / `suffix_get_dest_name()` (`src/xz/suffix.c`):
  - no destination name: "Filename has an unknown suffix, skipping" (decompress) or "File already has '%s' suffix, skipping" (compress), plus other `NULL` returns in `suffix.c`;
  - with `--force`, the old target cannot be removed (`unlink()` fails with something other than `ENOENT`);
  - `open()` with `O_CREAT | O_EXCL` fails, for example the target already exists and `--force` was not used;
  - DJGPP only: destination is a DOS special file, or "Output file is the same as the input file" (same `st_dev`/`st_ino`);
  - Windows (DOS-like, non-DJGPP): "Destination is not a regular file".
- `coder_normal()` leaves its loop without setting `success = true`:
  - `user_abort` set (loop condition `while (!user_abort)`), i.e. a signal arrived;
  - read error (`io_read()` returns `SIZE_MAX`);
  - write error (`coder_write_output()` -> `io_write()` returns true, including `user_abort` or `EPIPE` in `io_write_buf()`);
  - any liblzma return code that stops coding (everything except `LZMA_OK` and the warning-only `LZMA_UNSUPPORTED_CHECK`), such as `LZMA_DATA_ERROR`, `LZMA_MEMLIMIT_ERROR`, `LZMA_FORMAT_ERROR`;
  - `LZMA_STREAM_END` but there is still input left (trailing garbage) when `allow_trailing_input` is false: xz tries to read one more byte, and if it gets one it sets `ret = LZMA_DATA_ERROR`.
  `success = true` is set only at `LZMA_STREAM_END` with either `allow_trailing_input` or `strm.avail_in == 0` and `pair->src_eof`.
- `coder_passthru()` returns false on `user_abort`, write error or read error. (This path is only for `--decompress --stdout --force`, where `opt_keep_original` is already true, so it never deletes anyway.)
- In `io_close()` itself, `success` is turned to false when:
  - the final sparse-file step fails (`lseek()` fails: "Seeking failed when trying to create a sparse file", or the one zero byte `io_write_buf()` fails);
  - `io_close_dest()` returns true: `close(dest_fd)` failed ("Closing the file failed"; the destination is then unlinked as junk), or restoring stdout flags with `fcntl()` failed. The code comment says: "Close the destination first. If it fails, we must not remove the source file!"

When `success` is false, `io_close_dest()` removes the destination file instead (`io_unlink(pair->dest_name, &pair->dest_st)`), and the source is kept.

Not a blocker: `io_copy_attrs()` returns `void`. Failures to copy owner, group, mode or timestamps only give warnings (or are ignored) and do not stop the source from being deleted.

## Condition 4: the checks inside `io_unlink()`

`io_unlink(name, known_st)` (`file_io.c`, about line 231), on non-DOS-like systems:

- It does a fresh `lstat(name, &new_st)`, or `stat()` if `opt_force` is set.
- If that call fails, or `new_st.st_dev != known_st->st_dev`, or `new_st.st_ino != known_st->st_ino`, it prints the warning "%s: File seems to have been moved, not removing" and does not unlink.
  - On `__VMS` only `st_ino` is compared (with `memcmp`); `st_dev` is not compared.
- Otherwise it calls `unlink(name)`; on failure it warns "%s: Cannot remove: %s".

`known_st` is `pair->src_st`, filled by `fstat(pair->src_fd, ...)` in `io_open_src_real()` (`stat()` by name on DJGPP).

Limits of this check, stated in the code comments:

- There is still a race between `lstat()`/`stat()` and `unlink()`.
- With `--force`, `stat()` follows symlinks. If the regular file `foo` is renamed to `bar` and a symlink `foo -> bar` is created, xz thinks nothing changed and removes `foo` (the symlink).
- On `TUKLIB_DOSLIKE` systems (DOS/Windows) the device/inode check is compiled out ("st_ino is meaningless"); `unlink()` is called directly.

## Earlier checks that skip the file before any work (so nothing is deleted)

All in `io_open_src()` / `io_open_src_real()`; on failure `coder_run()` returns right away and `io_close()` is never called:

- Empty filename: "Empty filename, skipping".
- Symlink, unless `opt_stdout || opt_force || opt_keep_original` (`follow_symlinks`): opened with `O_NOFOLLOW` (or a separate `lstat()` where `O_NOFOLLOW` does not exist): "Is a symbolic link, skipping".
- `open()` or `fstat()` fails.
- Directory: "Is a directory, skipping".
- Not a regular file when `reg_files_only` (`!opt_stdout`): "Not a regular file, skipping". `--force` does not override this.
- Only when `reg_files_only && !opt_force && !opt_keep_original` (exactly the case where the source would be deleted), on non-DOS-like systems:
  - setuid or setgid bit set: "File has setuid or setgid bit set, skipping";
  - sticky bit set: "File has sticky bit set, skipping";
  - `st_nlink > 1`: "Input file has more than one hard link, skipping".

With `--force` these three checks are skipped and the file can still be deleted after success.

Also in `main()`: a `-` argument is skipped when compressed data would go to or come from a terminal, and the loop stops when `user_abort` is set.

## Things the code does not check

- It does not verify the contents of the output file (no read-back or compare) before removing the source. The decision rests on liblzma finishing, writes succeeding and `close()` of the destination succeeding.
- There is no `fsync()` of the destination in the functions I read (`io_close()`, `io_close_dest()`); I did not search the whole tree for a sync option.
- `io_unlink()` compares only device and inode numbers, not size or timestamps.
- I did not read the full bodies of `compressed_name()` / `uncompressed_name()` in `suffix.c`, only their warning messages and `NULL` returns.
