# Answer

# Q4: What mechanisms verify or constrain the integrity of test fixture files?

Short answer: at commit 7baf6835 there is **no cryptographic or checksum manifest** for the fixtures in `tests/files/` (no sha256/md5 list, no signature check, no script that hashes them). Integrity is constrained only indirectly, by seven mechanisms: behavioural tests keyed on the file name, a handful of content checks in C tests, a size/emptiness guard in the test loader, a licence allow-list by path, isolation of `tests/` from the build, a prose README (documentation only), and generating some inputs at test time instead of shipping them.

## 1. Behaviour contract by file name: `tests/test_files.sh`

The script globs `"$srcdir"/files/` and enforces an expected decoder result per name prefix. It never compares against a list of expected names or hashes.

| Glob | Tool(s) | Required result | Failure message |
|---|---|---|---|
| `good-*.xz` | `xz -dc` and `xzdec` | exit 0 | `Good file failed` |
| `bad-*.xz` | `xz -dc`; `xzdec` only if `NO_WARN` is empty | must fail | `Bad file succeeded` |
| `bad-3-index-uncomp-overflow.xz` | `xz -l` (extra check) | must fail | `Bad file succeeded with xz -l` |
| `unsupported-*.xz` | `xz -dc` only | must fail | `Unsupported file succeeded` |
| `unsupported-check.xz` | `xz -dcqQ`, `xzdec -qQ` | must succeed | `Unsupported file failed with ...` |
| `good-*.lzma` / `bad-*.lzma` | `xz -dc` | succeed / fail | same messages |
| `good-*.lz`; `bad-*.lz` + `unsupported-*.lz` | `xz -dc`, only if `have_feature LZIP_DECODER` | succeed / fail | same messages |

Details that matter:
- For good files the decoder itself verifies the embedded integrity check (CRC32/CRC64/SHA-256 in `.xz`, CRC32 in `.lz`), so a corrupted good fixture fails. Output goes to `/dev/null`; **decoded content is not compared to anything** here.
- For bad files only "non-zero exit" is checked, **not the specific error**. A bad fixture altered so that it fails for a different reason still passes.
- Feature gating: `have_feature()` greps `../config.h` for `HAVE_<X>` and skips a file (exit status 77) if a decoder is disabled. `NO_WARN=-qQ` is set when `HAVE_CHECK_CRC64` or `HAVE_CHECK_SHA256` is missing. The whole script exits 77 if neither `xz` nor `xzdec` was built or `HAVE_DECODERS` is absent.
- Stale patterns: the script still has `case` branches for `good-1-sparc-lzma2.xz`, `good-1-x86-lzma2.xz` and `good-1-riscv-lzma2-*.xz`, but no such files exist in `tests/files/` at this commit (harmless, they match nothing).
- Not enforced: the README rule that files "must not require a lot of CPU time or RAM". `test_files.sh` sets no `--memlimit` and no timeout.

Wiring: Autotools lists it in `TESTS` (`tests/Makefile.am`). CMake (`tests/tests.cmake`) adds it only when `UNIX AND HAVE_ALL_DECODERS AND HAVE_ALL_CHECKS AND XZ_LZIP_DECODER`, with `srcdir=${CMAKE_CURRENT_SOURCE_DIR}/tests`, `SKIP_RETURN_CODE 77`, and a dedicated working directory `test_files` so that the `../config.h` probe does not read outside the build directory.

## 2. C tests that pin specific fixtures (stronger checks, few files)

All load fixtures by hard-coded name via `tuktest_file_from_srcdir()`.

- `tests/test_lzip_decoder.c` — the only place where **decoded content is verified**. Constants `hello_world_crc = 0x15A2A343` (CRC32 of "Hello\nWorld\n") and `trailing_garbage_crc = 0x87081A60`. `basic_lzip_decode()` feeds one byte at a time, asserts `LZMA_STREAM_END`, `strm.total_in == file_size`, and the output CRC32. `trailing_helper()` also checks the CRC32 of the unconsumed trailing bytes. `test_concatenated()` covers `good-2-v0-v1.lz`, `good-2-v1-v0.lz`, `good-2-v1-v1.lz`. Bad files are checked for **exact** return codes through `decode_expect_error()` (e.g. `bad-1-v1-dict-1.lz`/`-2` give `LZMA_DATA_ERROR`), and `test_crc()` checks `bad-1-v1-crc32.lz` gives `LZMA_DATA_ERROR`, passes with the check ignored, and reports `LZMA_GET_CHECK` / `LZMA_CHECK_CRC32`.
- `tests/test_check.c` — `main()` loads `good-1-check-none.xz`, `unsupported-check.xz`, `good-1-check-crc32.xz`, `-crc64.xz`, `-sha256.xz` (last three under `HAVE_CHECK_*`); `test_lzma_get_check_st/mt` assert the check type the decoder reports for each.
- `tests/test_bcj_exact_size.c` — `test_empty_block()` decodes `good-1-empty-bcj-lzma2.xz` with `lzma_stream_buffer_decode()` and asserts `LZMA_OK`, `in_pos == in_size`, `out_pos == 0`.
- `tests/test_memlimit.c` — uses `good-1-check-crc32.xz` and `good-unknown_size-with_eopm.lzma`; asserts `LZMA_MEMLIMIT_ERROR` then `LZMA_STREAM_END`.
- `tests/test_scripts.sh` — `xzdiff` of `good-1-check-crc32.xz` vs `good-1-check-crc64.xz` must exit 0 (same payload), vs `good-1-lzma2-1.xz` must exit 1, vs missing file must exit 2. `xzgrep` output on copies of `good-1-lzma2-1.xz` and `good-2-lzma2.xz` is compared with `cmp -s` to the checked-in `tests/xzgrep_expected_output`. This indirectly pins the decoded text of those four files.

## 3. Loader guard: `tuktest_file_from_x()` in `tests/tuktest.h`

Behind the macros `tuktest_file_from_srcdir` (prefix `getenv("srcdir")`) and `tuktest_file_from_builddir`. It rejects: NULL or empty filename, NULL size pointer, open failure, seek/tell failure, **empty file** ("File is empty"), **size > `TUKTEST_FILE_SIZE_MAX`** (`64L << 20`, 64 MiB, overridable with `#ifndef`), read error, short read, close error. Any of these is a hard error through `tuktest_error_impl` (exit status `TUKTEST_EXIT_ERROR` = 99, remaining tests not run). The comment says: "The assumption is that something is wrong in these cases." It checks size and readability only, not content.

## 4. Licence allow-list by path: `build-aux/license-check.sh`

Every file must carry an SPDX tag or match an allow-list. Fixtures are covered by `PAT_UNTAGGED_0BSD`:
- `^tests/files/[^/]+\.(lz|lzma|xz)$`
- `^tests/xzgrep_expected_output$`
- `^(.*/)?README$`

Effect: an untagged file in `tests/files/` with **another extension**, or in a **subdirectory** of it, is reported as "ERROR: Licensing is unclear" with exit status 1. It runs on `git ls-files` (or `find` in an unpacked tarball) from `dist-hook` and `mydist` in the top-level `Makefile.am`, so it gates release tarball creation. It does **not** look inside the binary files: any new `.xz`/`.lzma`/`.lz` file directly in `tests/files/` passes automatically.

## 5. Isolation of tests from the build

- `CMakeLists.txt` ends with `include(tests/tests.cmake OPTIONAL)`. The header of `tests/tests.cmake` states the purpose: one can delete the whole `tests` directory and still build, "This way it's easy to ensure that nothing in the 'tests' directory can affect the build process." NEWS 5.6.2 repeats this (`rm -rf tests`).
- Outside `tests/`, nothing in the build reads the fixtures: the only non-test references to `tests/files`, `good-` or `bad-` names are docs (`README`, `INSTALL`), `license-check.sh`, and unrelated matches. `m4/` contains no `build-to-host.m4`.
- Autotools ships the directory as-is: `EXTRA_DIST = files ...` in `tests/Makefile.am`. This is not checked the same way: no Autotools-side equivalent of the "delete tests" guarantee was found beyond `tests` being a separate `SUBDIRS` entry.

## 6. Provenance and reproducibility (documentation, not enforced)

- `tests/files/README` describes each file and its expected class. It admits many files were "created by hand with a hex editor, thus there is no better 'source code' than the files themselves."
- I cross-checked: all 95 fixture files are named in the README and every name in the README exists. **No script enforces this**; it was a manual check.
- Only two files have a recreation recipe: `good-1-arm64-lzma2-1.xz` and `-2.xz`, via `debug/testfilegen-arm64.c` piped to `xz -T1 -Ccrc32 --arm64 ...` ("XZ Utils 5.4.x (newer may or may not work too)"). No test regenerates and compares them.
- NEWS 5.6.2: backdoor removed (CVE-2024-3094), and two tests using x86 and SPARC object files removed because "the object files aren't easy to reproduce". Git history for `tests/files` shows `e93e13c8` (backdoor removal) and `a5f2aa56` (remove x86 and SPARC BCJ tests).
- All fixtures are small: the largest is `good-1-delta-lzma2.tiff.xz` at 51316 bytes; the rest are 528 bytes or less. This is a property of the tree, not an enforced limit (the only enforced limit is the 64 MiB one in section 3).

## 7. Inputs generated at test time instead of shipped

`tests/create_compress_files.c` writes `compress_generated_abc`, `_random`, `_text` into the build directory (only if missing). `tests/test_compress.sh` round-trips them and verifies with `cmp` against the original, for `xz` and `xzdec`, under `--memlimit-compress=48MiB --memlimit-decompress=5MiB --no-adjust --threads=1`. The script has a `compress_prepared_*` branch for source-tree files, but no such file exists at this commit. `.gitignore` lists the generated files so they are not committed.

## Not present / not checked

- No hash or signature manifest for `tests/files/`; no `sha256sum`/`md5sum`/`gpg` use in tests or build files.
- No check that the set of fixture files matches a list (a new `bad-*.xz` or `good-*.xz` is picked up by the glob automatically).
- No binary markers for fixtures in `.gitattributes` (it only has `export-ignore` lines). `.codespellrc` does not mention them.
- `tests/ossfuzz/` ships no seed corpus: only three fuzz targets, `.options` files (`max_len = 4096` for two of them) and two dictionaries. `fuzz_common.h` sets `MEM_LIMIT (300 << 20)`. It does not read `tests/files/`.
- CI (`.github/workflows/ci.yml` with `build-aux/ci_build.bash`) runs the test suite in many configurations, including `-fsanitize=address,undefined` and Valgrind, so decoding the fixtures is memory-checked there. I read only the grep'd lines of these two files, not all of them.
